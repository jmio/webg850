# BSAVE / BLOAD エミュレーションの仕組み

BASIC の `BSAVE` が 11pin へ出力する内容をエミュレータ側で復号してファイルに落とし、
逆にファイルの内容を 11pin の入力へ流し込んで `BLOAD` で書き戻す仕組み。

- 信号そのものの形式 → [../analysis/bsave-signal-format.md](../analysis/bsave-signal-format.md)
- 保存されるファイルの形式 → [bsave-file-format.md](bsave-file-format.md)
- I/O ポートの一覧 → [../analysis/io-ports.md](../analysis/io-ports.md)

## 全体像

```
                 BSAVE (取り出し)

  ROM の送出ルーチン
        |  OUT (18H)  bit7 を H/L させる
        v
   out18()  ──→  bsaveCapture()      H 期間を測ってビット列へ
                      |
                      v
                 bsaveDecode()        ヘッダを読み飛ばし 9 ビット 1 組をバイトへ
                      |
                      v
                 bsaveFinish()        2 ブロックを連結
                      |
                      v
                downloadBinary()  ──→  bsave.bin


                 BLOAD (書き戻し)

   bsave.bin  ──→  bloadLoadFile()     ファイルを読む
                      |
                      v
                  bloadBits()          ヘッダ・データ・パリティのビット列を作る
                      |
                      v
                  bloadBuild()         PULSES を含む波形を
                      |                立ち上がり/立ち下がりの時刻の列にする
                      v
                  bloadPoll()  ←──  in1f()   ROM が 3usec 間隔で読みに来る
                      |                       IN (1FH) bit2
                      v
                 ROM の受信ルーチン
```

## 前提となる時刻の扱い

パルスの長さを測るにも作るにも、**フレームをまたいで連続する時刻**が要る。
エミュレータは `setInterval` で 1 フレームずつ実行するため、フレーム内の経過時間しか
持っていなかった。そこで累積のステート数を追加した。

```js
var z80totalStates = 0;                 /* run() で 1 フレーム分ずつ加算 */

function z80states() {
	return z80totalStates - z80restStates;
}
```

`z80restStates` は「まだ消化していないステート数」なので、与えた総数から引けば
消化済みのステート数（＝経過時間）が正確に求まる。**フレーム内の近似ではない。**

2806 バイトのプログラムの転送はフレーム境界を数百回またぐが、この方式で
パルス幅の判定がずれないことを確認している。

## BSAVE 側（取り出し）

### 取り込み

`out18()` から `bsaveCapture(x)` を呼ぶ。データ線は `0x18` の **bit7** のみ。

1. レベルが変化したときだけ処理する
2. 立ち上がりで時刻を記録する
3. 立ち下がりで H 期間が確定する。長さで意味が決まる
   - 250usec 未満 → ビット **0**
   - 250usec 以上 1000usec 未満 → ビット **1**
   - 1000usec 以上 → **区切りのパルス**

しきい値は `BSAVE_BIT_US` / `BSAVE_MARK_US` で定義している。

### 転送の終わりの判定

区切りのパルスは PULSES1 に 1 回、PULSES2 に 2 回、PULSES3 に 1 回の**合計 4 回**現れる。
**4 回目を検出した時点で 1 回の転送が終わった**とみなし、復号に移る。

区切りで区切られた区間のうち、ビットを含むものが PWM1 と PWM2 の 2 つになる。

### 復号

`bsaveDecode(bits)` がヘッダ（0 の並び → 1 の並び → 0 の並び）を読み飛ばし、
スタートビットの後ろから 9 ビット 1 組を取り出して MSB ファーストでバイトに組み立てる。
末尾 2 バイトはパリティとして分離し、データ部の 1 の個数と一致するかを確認できるようにしている。

`bsaveFinish()` が PWM1 の 48 バイトと PWM2 のメインデータを連結し、デバッグ窓へ

```
BSAVE: mode=02 size=2806(申告 2806) parity=OK/OK
```

のように結果を出したうえで `downloadBinary()` へ渡す。

### なぜ downloadData() を使わないか

既存の `downloadData()` は先頭で `console.log(content)` を実行する。
デバッグ窓は `console.log` を横取りしているため、バイナリを渡すと
中身が JSON 化されて窓に流れ込む。そのため `downloadBinary()` を別に用意した。

## 保存するファイル名

`BSAVE "名前"` の名前は、ヘッダの `0x01`-`0x10` に左詰め・空白埋めで入る。
これに `.bin` を付けたものをブラウザが保存するときのファイル名にする。

| BASIC で打つもの | 保存されるファイル名 |
|:--|:--|
| `BSAVE` | `bsave.bin` |
| `BSAVE "MYPROG"` | `MYPROG.bin` |
| `BSAVE "test1"` | `test1.bin` |

ファイル名に使えない文字（空白や `/` など）は `_` に置き換える。
名前は 16 文字までで、それはヘッダの領域の大きさによる制限。

## 進行状況の表示

1 回の転送に 20 秒以上かかるため、画面のパネルに進み具合を出している。

- 取り出し中は `BSAVE 受信中 1/2 47%` のように、ブロック番号と割合
- 書き戻し中は `BLOAD 送出中 62%`
- 終わると `BSAVE 完了 70 byte` などが残る

割合は次のように求めている。

- **PWM1 は常に 10,532 ビット**。ヘッダ 48 バイトは固定長なので、
  ヘッダの 0 が 10,000 個 + 1 が 40 個 + 0 が 40 個 + START_BIT + 9 ビット × 50 組 + STOP_BIT
  （送出側で短縮した場合も、受信する波形は実機の ROM が作るものなのでこの値になる）
- **PWM2 は PWM1 を復号すれば決まる**。区切りのパルスで PWM1 が閉じた時点で
  `bsaveDecode()` を呼んでメインデータのサイズを取り出し、
  `25888 + 1 + (サイズ + 2) × 9 + 1` を総ビット数とする

更新は `run()` から 1 フレームに 1 回だけ行う。`bsaveCapture()` の中で毎回 DOM を
書き換えると重くなるため。

## BLOAD 側（書き戻し）

### 波形の組み立て

`bloadBits()` が 1 ブロック分のビット列を作る。

```
ヘッダの 0 の並び → 1 の並び → 0 の並び
→ START_BIT (1)
→ [1 + 8 ビットのデータ] × バイト数
→ [1 + 8 ビットのパリティ] × 2
→ STOP_BIT (1)
```

ヘッダの個数は PWM1 が `0×10000, 1×40, 0×40`、PWM2 が `0×25848, 1×20, 0×20`。

`bloadBuild()` がこれに PULSES を足して、**立ち上がり・立ち下がりの絶対時刻の列**にする。
各ビットは「H を t、続けて L を t」で、t はビットが 0 なら 145usec、1 なら 360usec。

### 読み出し

`in1f()` が `bloadPoll()` を呼ぶ。

```js
function in1f() {
	return keyBreak | bloadPoll() | (sioEnable ? 0x02: 0x00);
}
```

`bloadPoll()` は現在時刻まで時刻の列を進めてレベルを反転させ、
H なら `BLOAD_BIT`（`0x04` = bit2）を返す。**`keyBreak`（bit7）は必ず残す。**
bit7 は BREAK キーの検査に使われており、立ててしまうと転送が中断される。

### 送出開始の検知

ファイルを読んだ時点で波形を流し始めると、利用者が `BLOAD` を打つ前に先頭が流れてしまう。
かといって ROM のアドレスを見張るのは ROM の版に依存する。

そこで**読み出しの間隔**で判定している。

| 状態 | `in1f()` が読まれる間隔 |
|:--|:--|
| 待機中（BASIC のコマンド待ち）| 1 フレームに 1 回程度 |
| `BLOAD` のポーリング中 | **約 3usec（27 ステート）** |

`in1f()` が前回から **500 ステート未満**で再び読まれたらポーリングが始まったとみなし、
その時刻を起点に波形の時刻列を平行移動させて流し始める。
ROM のアドレスに依存しないため、ROM の版が違っても動くはずである。

### 送出中は取り込みを止める

`bsaveCapture()` は送出中（`bloadEdges != null || bloadArmed`）なら何もしない。
これが無いと、BLOAD 中に ROM が `0x18` へ出す信号を拾って
誤った復号結果を出してしまう。

### 取り込みの状態はどこで初期化するか

`bsaveReset()` は転送完了時のほかに、**`out60_g850()`（11pin の動作モード設定）からも呼ぶ。**

`BSAVE` も `BLOAD` も、転送を始める前に必ず `OUT 60,0` で 11pin を
3-In 3-Out モードにする（[../analysis/11pin-uart.md](../analysis/11pin-uart.md) の実測を参照）。
つまりここは**転送の開始点**であり、状態を初期化するのにちょうどよい。

これが無いと、転送を BREAK で中断したときに区切りの検出数が途中のまま残る。
実測では中断後に区切りの数が 2、ブロックが 1 個残った状態で止まった。
その状態で次の `BSAVE` を始めると、**区切りを 2 回検出しただけで転送が終わったと
誤認する**ことになる。

無通信時間で判定する方法も考えられるが、PULSES1 の L が正常時でも 7 秒あるため
しきい値を大きく取らざるを得ず、中断からの復帰が遅くなる。

## 送出波形の短縮

実機の波形をそのまま流すと、22 バイトで 23.3 秒、2806 バイトで 35.6 秒かかる。
待ち時間の大半は PULSES の長い L と、ヘッダの 0 の並びである。

**受信側がこれらをどこまで短くしても受け取れるかを実測し、短縮した波形を送っている。**

### 実測した下限

`10 REM UUUU`（本体 22 バイト）で、値を変えながら BLOAD が成功するかを調べた。
試行ごとに REM の中身を変えて一意な目印にし、RAM 上にその目印が現れるかで判定している
（`NEW` は RAM のバイト列までは消さないため、同じ内容で試すと前回の残骸を拾ってしまう）。

| 変えたもの | 結果 |
|:--|:--|
| PULSES の長い L を 1/100（`p1L` 71ms、`p2L` 17.8ms、`p3L` 35.6ms）| 成功。23.3 秒 → 11.0 秒 |
| さらにヘッダを 1/2（10000 → 5000、25848 → 12924）| 成功。5.8 秒 |
| ヘッダを 1/4（2500 / 6462）| 成功。3.2 秒 |
| ヘッダを 1/6（1666 / 4308）| **失敗** |
| ヘッダを 1/10（1000 / 2585）| **失敗** |

どちらのヘッダが効いているかを切り分けた。

| 条件 | 結果 |
|:--|:--|
| PWM1 のヘッダだけ 1666、PWM2 は 6462 | **失敗** |
| PWM1 のヘッダ 2500、PWM2 だけ 4308 | 成功 |
| PWM1 のヘッダ 2000、PWM2 5170 | 成功 |
| PWM1 のヘッダ 1800 | **失敗** |
| PWM1 のヘッダ 2500、PWM2 2000 | 成功 |
| PWM1 のヘッダ 2500、PWM2 1000 | **失敗** |

**PWM1 のヘッダの下限は 1800〜2000 ビット、PWM2 のヘッダの下限は 1000〜2000 ビット。**
PULSES の長い L は 1/100 にしても影響が無かった。

### 採用した値

下限の約 2 倍の余裕を取って、どちらのヘッダも **4000 ビット**にした。
PULSES の長い L は 1/100 のままとした。

| 定数 | 採用値 | 実機相当 |
|:--|:--|:--|
| `BLOAD_P1_L_US` | 71,110 | 7,111,000 |
| `BLOAD_P2_L_US` | 17,780 | 1,778,000 |
| `BLOAD_P3_L_US` | 35,560 | 3,556,000 |
| `BLOAD_HZ1` | 4,000 | 10,000 |
| `BLOAD_HZ2` | 4,000 | 25,848 |

`BLOAD_MARK_US`（区切りのパルス）と PULSES2 の短い L は変えていない。
実機と同じ波形を流したいときは、コメントに書いてある実機相当の値に戻せばよい。

### 効果と確認

| 本体のサイズ | 変更前 | 変更後 |
|:--|:--|:--|
| 22 バイト | 23.3 秒 | **2.9 秒** |
| 2806 バイト | 35.6 秒 | **15.2 秒** |

中断からの復帰も確認した。`BSAVE` を BREAK で中断すると区切りの数が 2、
ブロックが 1 個残るが、次の `BSAVE` を始めた時点で 0 に戻り、正しく完走する。

- 22 バイトは 3 回連続で成功
- 2806 バイトは 2 回連続で成功。さらに実際の `bloadBuild()` を使った通しでも成功
- 大きなプログラムほどデータ本体の時間が支配的になるため、短縮の効果は小さくなる

## 使い方

### 取り出す

1. 画面の **BSAVE CAPTURE** にチェックを入れる（既定は無効）
2. BASIC で `BSAVE` または `BSAVE "名前"` を実行する
3. 転送が終わるとファイルがダウンロードされる。進行状況はパネルに出る

### 書き戻す

1. 画面の **LOAD BIN** ボタンでファイルを選ぶ
2. 「読み込みました」と出たら BASIC で `BLOAD` を実行する
3. 転送が終わるとデバッグ窓に「送出完了」と出る

`BSAVE CAPTURE` は書き戻しのときはオフでもオンでもよい（送出中は自動で止まる）。

## 既知の制約

- **取り出し (BSAVE) は短縮できない。** 送出しているのは ROM なので、
  22 バイトで 23.3 秒、2806 バイトで 35.6 秒かかる。進行状況を画面に出している。
  書き戻し (BLOAD) は波形を短縮してある（2.9 秒 / 15.2 秒）。
- **`15H`（Xin 入力イネーブル）を見ていない。** 実機では `1FH` の入力は
  `15H` で有効にしないと読めないが、エミュレータは `15H` を未対応にしているため、
  その設定に関係なく入力が読める。`BLOAD` が実際に `OUT 15H,90H` を出していることは
  確認済み。忠実にするならここをゲートすべきだが、どのビットが有効化なのかが
  分かっていないため実装していない。
- **TEXT モードの `Sio` とは別系統。** あちらは同じ `0x18` bit7 を使うが変調が違い、
  `0x1F` では bit1 を使う（[text-sio-capture.md](text-sio-capture.md)）。混同しないこと。
- `BSAVE "名前"` の名前はファイル名に使うだけで、`BLOAD` 側で名前を照合していない。
