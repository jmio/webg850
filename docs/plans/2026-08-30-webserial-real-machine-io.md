# 実装計画: BSAVE / BLOAD の相手をファイルと実機から選べるようにする

作成日: 2026-08-30
状態: **完了**（2026-08-30）

## 目的

エミュレータの `BSAVE` の出力先と `BLOAD` の入力元を、**ファイル**と
**Web Serial 経由の実機**から選べるようにする。

実機との橋渡しは [arduino-11pin/](../../arduino-11pin/) で確立済みで、
Arduino Uno R4 Minima 経由で実機の 11pin I/O に対して 2854 バイトの往復が
バイト単位で一致することを確認してある。本計画はその成果をブラウザから
直接使えるようにするもの。

## ゴール（完了条件）

1. `BSAVE 先` を「ファイル」「実機」から選べる
2. `BLOAD 元` を「ファイル」「実機」から選べる
3. 実機を選んだとき、エミュレータの BASIC プログラムが実機へ渡り、
   実機の BASIC プログラムがエミュレータへ戻る
4. 進捗が画面に出る（転送に 20〜40 秒かかるため必須）
5. **Web Serial が使えない環境でも従来どおり動く**（実機の選択肢を出さない）

## 用語の注意（混乱しやすい）

「BSAVE 先 = 実機」のとき、**実機側で実行するのは `BLOAD`** である。
エミュレータが「保存」する先が実機なので、実機は「読み込む」側になる。

| 画面上の選択 | エミュレータで実行 | 実機で実行 | 波形の向き |
|:--|:--|:--|:--|
| BSAVE 先 = ファイル | `BSAVE` | — | — |
| **BSAVE 先 = 実機** | `BSAVE` | **`BLOAD`** | Arduino → 実機 |
| BLOAD 元 = ファイル | `BLOAD` | — | — |
| **BLOAD 元 = 実機** | `BLOAD` | **`BSAVE`** | 実機 → Arduino |

UI の文言はこの取り違えを防ぐことを最優先にする。

## 実行環境と制約

### Web Serial が使える条件（2026-08-30 実測・確定）

**Firefox の `file://` でそのまま動く。サーバは要らない。**

| ブラウザ | `file://` | `http://127.0.0.1:8850/` |
|:--|:--|:--|
| **Firefox** | **使える**（`PONG g850-11pin 0.6.0`）| **使える**（同左）|
| Chrome / Edge | 未確認 | 未確認 |

**主環境（Firefox + `file://`）を一切変えずに実機連携を足せる。**
`tools/serve.py` を立てる必要は無い。

| 条件 | 内容 |
|:--|:--|
| 操作 | `navigator.serial.requestPort()` は**ユーザー操作から呼ぶ**必要がある |
| 許可の保存 | **されない。** 再読み込み後の `getPorts()` は 0 |

**許可が保存されないので `getPorts()` を当てにしない。**
接続は常に `requestPort()` から始める。ページを開き直すたびに
[接続] を押してダイアログでボードを選ぶ運用になる。
1 回の作業で何度も転送するので、実用上の負担にはならない。

`navigator.serial` が無い環境では実機の選択肢を出さずファイルのみで
動かす。**既存の動作は一切変えない。**

### ポートの排他

ブラウザがポートを掴んでいる間、`arduino-11pin/host/g850ctl.py` は使えない。
切り分けのときに困るので、**切断ボタンを必ず用意する**。

## 実験から持ち込む前提（すべて実機で確認済み）

詳細は [arduino-11pin/docs/experiment-log.md](../../arduino-11pin/docs/experiment-log.md)。

### やり取りの単位は `.bin`

**信号形式の知識をブラウザ側に持ち込む必要は無い。**
エミュレータは既に `.bin` を読み書きできる（`bsaveFinish` / `bloadLoadFile`）。
波形のタイミング・極性・パリティはすべてファームウェアの中にある。
Web Serial 層は **`.bin` を運ぶだけ**でよい。

### プロトコルの性質

| 事項 | 内容 |
|:--|:--|
| 終端 | **`+OK` で始まる行か `!` で始まる行の 2 つだけ** |
| 種別 | `+` データ / `!` エラー(終端) / `#` 情報 / `*` 進捗 |
| 文字 | **ASCII のみ。** 日本語は入らない |
| ボーレート | USB CDC なので実効的に無関係 |
| 中断 | `ESC` (0x1B) か `Ctrl-C` (0x03) を**生の 1 バイト**で送る |

### `LOAD`（ブラウザ → デバイス）

- **フロー制御は要らない。** 12288 バイト（27652 文字・384 行）を
  **1 回の `write` で投げてよい**。`+RDY` を待たなくても通る
- **1 行は 92 バイトまで。** 既定の 32 を変える理由は無い
  （1 行を長くしても 638 → 606 ms でほとんど速くならない。
  律速はデバイス側の行の解釈）
- **行と行の間を 10 秒以上空けない**（`!ERR timeout`）
- **エラーは 1 行で終わる。** デバイスが残りを読み捨てるので、
  `!` を見たらそのまま次のコマンドを送ってよい
- 速度: ASCII 42 KB/s、実データ 19 KB/s

### `CAP`（デバイス → ブラウザ）

- `+D <ブロック> <オフセット> <16進>` が 32 バイトごとに届く
- **ブロック 1 = ヘッダ 48 バイト、ブロック 2 = 本体。
  どちらも末尾 2 バイトはパリティなので落とす**
- `+R` にパリティの照合結果と `fe`（フレーミングエラー）が出る
- **進捗は `bits` を使う。`bytes` ではない。**
  PWM2 のヘッダ 25848 ビットを読み飛ばす **8.4 秒間は 1 バイトも
  復号されない**ので、`bytes` を見ていると止まって見える
- `#cap begin` が転送の開始を示す
- **取り込みは約 40 秒かかり、短縮できない**（実機が本来のヘッダと
  長い PULSES をそのまま出すため）

### `PLAY`（デバイス → 実機）

- 2854 バイトで **17.5 秒**（起動時の既定 `PROFILE FAST`）
- 送出中は `*PLAY <済>/<総数> <%>` が届く

### 待機してから合図する

**取り込みは、待機に入ったことを確認してから利用者に合図する。**
確認せずに合図すると転送の途中から拾い、ヘッダを取り逃がす。
実験でこれを 1 回やって失敗した。`#cap armed` を受け取ってから
「実機で BSAVE を実行してください」を出すこと。

### 別個体では較正が要る

焼き込んである値は 1 台（PC-G850V）の実測値。別の個体では `CAL` から
やり直す。**この計画では扱わない**（`g850ctl.py` で行う）。

## 設計

### モジュール構成

新規ファイルを 2 つ足し、`g800main.js` への変更は最小にする。

```
webserial.js      Web Serial のプロトコル層（G850Link）
realio.js         BSAVE/BLOAD の相手選択と画面まわり
g800main.js       分岐点を 2 か所だけ足す
webg850v.htm      <script> 2 行と UI
```

**`g800main.js` は 115 KB あり、エミュレータ本体である。**
実機連携の都合でここを太らせない。触るのは次の 2 か所だけにする。

1. `bsaveFinish()` の `downloadBinary` の直前に分岐を入れる
2. `bloadLoadFile()` の中身のうち「バイト列 → `bloadBuild`」を関数に
   切り出し、実機側からも呼べるようにする

### プロトコル層 `G850Link`（webserial.js）

```js
class G850Link {
    async connect()                    // requestPort + open + PING で確認
    async disconnect()
    async command(line, opts)          // +OK まで読む。! なら reject
    async load(bytes, onProgress)      // LOAD + D行 + END
    async play(onProgress)             // PLAY
    async capture(onProgress, signal)  // CAP。.bin を返す
    abort()                            // ESC を 1 バイト
}
```

**読み取り**: `port.readable` → `TextDecoderStream` → 行分割の
`TransformStream`。1 行ごとに種別で振り分ける。

**書き込み**: `TextEncoderStream` は**使わない**。中断の `ESC` を生バイトで
送る必要があるので、`port.writable.getWriter()` に対して `TextEncoder` で
手動符号化する。

**接続の確認**: 開いたら `PING` を送り、`+PONG g850-11pin <版>` を確認する。
別のシリアル機器を選んでしまったときに、そこで止められる。
フェーズ 0 で実際に動かして確かめた。

**`getPorts()` を当てにしない**。許可が保存されないので、
接続は常に `requestPort()` から始める。

**注意**: `pipeThrough` はストリームをロックする。切断時に
`reader.cancel()` → `readableStreamClosed.catch()` → `port.close()` の順で
確実に解放しないと、次の接続で失敗する。

### `.bin` の組み立て（受信側）

`CAP` の `+D` 行から `.bin` を作る手順。

1. ブロック番号ごとにオフセット順で連結する
2. **各ブロックの末尾 2 バイト（パリティ）を落とす**
3. ブロック 1 が 48 バイトであることを確かめる
4. ブロック 1 + ブロック 2 を連結して `.bin` にする
5. ヘッダの `0x12` の 16 ビット（リトルエンディアン）とブロック 2 の
   長さが一致することを確かめる

`+R` の `parity ... OK/NG` と `fe=0` も確認し、どれかが崩れていたら
**エミュレータへ流し込まずに中止する**。壊れたデータを BASIC 領域に
書き込むと復旧が面倒になる。

### 画面

**キーボードの隣（`main2`）に独立した節として置く。**

```
+--------+-------------------+
| [接続] | [ ] 実機とやり取り  |
|        | BSAVE→実機/BLOAD←実機 |
|        | BLOAD は自動で始まる  |
+--------+---------+---------+
| [送出]           | [中断]   |
+------------------+---------+
| (進捗バー)                  |
+----------------------------+
| 未接続                      |
+----------------------------+
```

取り込みのボタンは置いていない（→ [入口を一本化した](#入口を一本化した2026-08-30-追記)）。

`navigator.serial` が無ければ `REALIOROW` の行をまとめて隠す。

**置き場所の制約（実際に 2 回崩した）**

| 崩れ方 | 原因 | 対策 |
|:--|:--|:--|
| 画面全体が縮小された | 入れ子テーブルの `white-space:nowrap` が `table-layout:fixed` の親を押し広げ、`#device { width: max-content }` が大きくなって `fitDevice()` が縮小した | 入れ子テーブルをやめ、`width` と `table-layout:fixed` を明示する |
| 液晶とキーボードの間が空いた | デバッグ表 (`main1`) は液晶と高さが釣り合っている。行を足すと必ず下に隙間ができ、行数を削っても消えない | キーボードの隣 (`main2`) へ移す。右が空いているので高さに影響しない |

**選択はチェックボックス 1 つにした。** BSAVE の出力先と BLOAD の入力元を
別々に選ぶ形から変更している。実機をつないでいるとき片方だけファイルに
する理由が無く、幅も 440px から 270px に縮んだ。

ただし **`BSAVE → 実機 / BLOAD ← 実機` の一行は画面に残す。**
保存と読み込みで実機側の操作が入れ替わる（エミュレータが `BSAVE` する
とき実機は `BLOAD`）のが直感に反するため。

### 操作の流れ

**BSAVE 先 = 実機**

1. 利用者がエミュレータで `BSAVE` を実行 → `bsaveFinish()` が `.bin` を作る
2. 画面に「**実機で `BLOAD` を実行してから [送出] を押してください**」
3. [送出] → `LOAD`（1 秒未満）→ `PLAY`（17.5 秒）
4. `*PLAY` の進捗を表示
5. 完了後「実機の画面右下に `*` が出れば成功」と案内する

**待たせるのは実機側**にする。実機の `BLOAD` は `BREAK` するまで待ち続ける
ので、先に待たせておけば取りこぼしが無い。

**BLOAD 元 = 実機**

1. エミュレータで `BLOAD` を実行（または [実機から LOAD]）→ `CAP` を送る
2. **`#cap armed` を受け取ってから**「実機で `BSAVE` を実行してください」
3. `#cap begin` で「転送開始」に切り替え、`*CAP` の `bits` で進捗を出す
4. `+OK` で `.bin` を組み立て、パリティを確認
5. `bloadBuild()` に渡して `bloadArmed = true`
6. 「**エミュレータで `BLOAD` を実行してください**」

### 入口を一本化した（2026-08-30 追記）

はじめは [取込] だけを入口にしていた。これを次の順で直している。

1. **`LOAD BIN` も実機へ回す。** チェックが入っているのに `LOAD BIN` が
   ファイル選択を開き、`BSAVE` 側（自動で実機へ回る）と食い違っていた。
   `bloadLoadFile()` の先頭に `realioBloadSource()` を置き、
   `realioBsaveSink()` と同じ形で分岐させた。
2. **`BLOAD` の待機そのものを検出する。** `bloadPoll()` はもともと
   「ポート `0x1F` を細かい間隔で読み続けている＝`BLOAD` が待っている」を
   見て送出を始めていた。この判定は `bloadArmed`（用意済み）のときしか
   参照していなかったので、未準備のときにも見るようにして `bloadDemand()`
   を呼ぶ。実機モードなら `CAP`、そうでなければファイル選択を開く。
3. **[取込] を消した。** 1 と 2 で入口が三つになり、どれも同じ処理に
   なっていた。実機から受けるときはエミュレータで `BLOAD` を実行すれば
   よく、先に用意しておきたいときは [実機から LOAD] がある。

**待ちに入ってから用意しても間に合う。** `bloadPoll()` の起動条件は
「armed かつ細かい間隔で読まれている」なので、待っている最中に
`bloadSetBytes()` を呼べば次のポーリングでそのまま送出が始まる。実機の
`BLOAD` が `BREAK` するまで待ち続けるのと同じ挙動になる。ブラウザで実測し、
`armed` にした直後の 1 回の `in1f()` で送出が始まることを確認した。

### ファイル選択は自動で開かないことがある

ブラウザは利用者の操作から 5 秒以内（transient activation）でないと
ファイル選択を開かない。**例外も出ず、黙って無視される。**

| `BLOAD` の実行のされ方 | ファイル選択 |
|:--|:--|
| 手で `BLOAD` [ENTER] と打った | 開く。キー入力から数十 ms 後に検出される |
| `RUN` したプログラムの途中で `BLOAD` | 開かない。activation が切れている |
| 実機モード（Web Serial） | 関係ない。ポートは接続済み |

そのため **[ファイルから LOAD] ボタンは逃げ道として残す。** 押せば
`BLOAD` の待機中でもそのまま読み込める。

### 誤検出と負荷の実測（Chrome、2026-08-30）

見ているのは「`BLOAD` かどうか」ではなく「`0x1F` を細かく読み続ける
ループかどうか」でしかない。連続が 256 回続くまで発火させないことと、
`BSAVE/BLOAD 自動` のチェックで切れることで折り合いをつけている。

| 測ったもの | 値 |
|:--|:--|
| `in1f()` の呼び出し（BASIC 待機中）| 237 回/秒、最小間隔 39584 ステート（しきい値 500 の 79 倍）|
| `in1f()` の呼び出し（理論上の最大）| `IN A,(n)` は 11 ステート、最短ループで 23 ステート → 約 40 万回/秒 |
| `bloadPoll()` 1 回 | 2.8ns（呼び出しだけの 0.8ns を差し引いた値）|
| `bsaveCapture()` 1 回（チェック無効）| 1.7ns |
| `bsaveCapture()` 1 回（毎回がエッジ）| 5.5ns |
| 最悪時の負荷 | 40 万 × (2.8 + 5.5)ns ≒ 3.3ms/秒 = **0.33%** |
| BASIC 待機中の誤検出 | 13.8 秒走らせて 0 回 |

負荷が無視できるので**チェックは既定で ON**にし、`BSAVE` の取り込みと
`BLOAD` の検出を 1 つのスイッチにまとめた（`bsaveEnable`）。どちらも
「ポートを覗いて勝手に始まる」機能で、外したい場面（11pin を直接叩く
機械語プログラム）が同じだから。外しても、ボタンからの読み込みと送出、
実機とのやり取りは動く。

### 音と同じピンを見ている

**ポート `0x18` の bit7 は音声出力と共用**（`out18()` の `x & 0xc0` が
`waveOn` / `waveOff` を書く）。`BSAVE` の取り込みを既定で ON にすると、
`BEEP` の波形も `bsaveCapture()` へ入ってくる。

- H 期間が 1ms 未満（1kHz 超）→ ビットとして `bsaveBits` に積まれ続ける
- H 期間が 1ms 以上（500Hz 以下）→ 区切りのパルスとみなし、4 つで
  `bsaveFinish()` が走る。復号は失敗して「BSAVE 復号失敗」と出るだけで
  ファイルは落ちない

前者は上限が無かったので `BSAVE_BITS_MAX`（40 万ビット）を置いて黙って
捨てる。正規の `BSAVE` は PWM2 が `25890 + (N + 2) * 9 + 1` で、RAM 全域の
32KB でも 32 万ビットに収まるため影響しない。

### `BLOAD` 中に「BSAVE 受信中 1/2 0%」が出た（修正済み）

自動検出を入れて初めて出た不具合。**`BLOAD` の待機中は、これまで存在
しなかった状態**である。以前は先に用意してから `BLOAD` を実行していたので
必ず `bloadArmed` が立っており、`bsaveCapture()` の入口で弾かれていた。

自動検出では「用意していないまま `BLOAD` が待っている」時間ができる。この間
`bloadEdges == null && !bloadArmed` なので取り込みが素通りし、ROM が待ち
ループでポート `0x18` へ出す信号を区切りのパルスと見て `bsaveMarks` が立つ。
表示は `bsaveMarks > 0` だけで出るため「BSAVE 受信中 1/2 0%」に化ける。

直し方は 3 つ。

| 直し方 | 何を防ぐか |
|:--|:--|
| `bsaveCapture()` の入口に `bloadDemanded` を足す | 待機中と、送出直後（ラッチが立ったまま）の取り込みを止める |
| `bloadDemand()` の頭で `bsaveReset()` | 待機を検出した時点で、集めかけを捨てる |
| 無音が `BSAVE_IDLE_SEC`（2 秒）続いたら `bsaveReset()` | 音などで立った `bsaveMarks` が居座らないようにする。`BSAVE` の波形は途切れないので誤って捨てない |

あわせて、実機から取り込んだときの「エミュレータで `BLOAD` を実行して
ください」も出したままにしない。`bloadPoll()` の送出開始と完了から
`realioBloadStarted()` / `realioBloadDone()` を呼ぶ。ファイルから読んだ
`BLOAD` で実機の欄が動かないよう、実機が渡したときだけ書き換える。

### 進捗の総ビット数

`*CAP` の `bits` に対する分母は計算できる。

```
PWM1 = 10000 + 40 + 40 + 1 + (48 + 2) x 9 + 1 = 10532
PWM2 = 25848 + 20 + 20 + 1 + (N  + 2) x 9 + 1
```

`N`（本体サイズ）はブロック 1 のヘッダで分かり、**PWM2 が始まる前に
確定する**。それまでは PWM1 の 10532 を分母にする。

### 既知の制限: 送出は 12288 バイトまで

ファームウェアの `.bin` バッファは 12288 バイトで、**RAM の制約から 13824
までしか増やせない**（ヒープ 8 KB とスタック 1 KB が固定）。実機の空き容量は
27286 バイトなので、

- **取り込み（実機 → エミュレータ）は全域に対応**（流す方式のため）
- **送出（エミュレータ → 実機）は 12288 バイトまで**

12288 を超える `.bin` は送出前に弾き、その旨を表示する。

将来の解決策は**送出も流す方式にすること**。ビット間の L 期間が 164 µs あり、
必要な受信速度は毎秒 787 バイトなので、取り込みと同じ理屈で成立するはずである
（未検証）。本計画の範囲外とする。

## 手順

### フェーズ 0: 実行環境を決める — **完了（2026-08-30）**

`tools/tmp/webserial-check.htm`（使い捨ての確認ページ）で実測した。

| 確認項目 | Firefox + `file://` | Firefox + `http://127.0.0.1:8850/` |
|:--|:--|:--|
| `navigator.serial` | あり | あり |
| `requestPort()` のダイアログ | 出る | 出る |
| `PING` の応答 | **`PONG g850-11pin 0.6.0`** | **`PONG g850-11pin 0.6.0`** |
| 再読み込み後の `getPorts()` | — | **0（保存されない）** |

ダイアログに「この決定を記憶する」に相当する選択肢は**無かった**。
利用者が保存し損ねたのではなく、この実装では保存されないということ。

**結論**

1. **Firefox の `file://` でそのまま動く。サーバは要らない。**
   当初「Firefox は Web Serial 非対応」と書いていたが**誤りだった。**
   確認を手順に組み込んでいたおかげで、誤った前提のまま
   実装に入らずに済んだ
2. **許可は保存されない。** `getPorts()` を当てにせず、接続は常に
   `requestPort()` から始める設計にする
3. Chrome / Edge は未確認。主環境ではないので後回しでよい

確認ページのプロトコル層（行分割・種別による振り分け・`+OK` / `!` での
終端判定）はそのまま `webserial.js` の下地に使える。

### フェーズ 1: プロトコル層 — **完了（2026-08-30）**

[`webserial.js`](../../webserial.js) に `G850Link` を書き、
`tools/tmp/webserial-phase1.htm`（使い捨ての検証ページ）で

| # | 試験 | 結果 |
|:--|:--|:--|
| 1 | 接続 + `PING` | `PONG g850-11pin 0.6.0` |
| 2 | JS の CRC が Python と一致 | `C945` / `B484` / `834C` |

`READLINE_TOOLONG` が**ブラウザから見ても正しく振る舞うか**の確認。
`!ERR` の次の行が `+PONG` になっており、入力を捨て直さずに
次のコマンドを送れることが確かめられた。

### フェーズ 5: 往復試験 — **完了（2026-08-30）**

```
basen.bin      (元・g850ctl.py で取得)       2854 byte crc=5576 sha=26f3e7f18c1ef6d4
capture.bin    (1 往復目・ブラウザ)          2854 byte crc=5576 sha=26f3e7f18c1ef6d4
capture(1).bin (2 往復目・実機 NEW+BLOAD 後) 2854 byte crc=5576 sha=26f3e7f18c1ef6d4
bsave(1).bin   (エミュレータ → ファイル)     2854 byte crc=5576 sha=26f3e7f18c1ef6d4
```

このデータが通った経路。

1. 実機 `BSAVE` → Arduino 取り込み → `g850ctl.py` → `basen.bin`
2. 実機 `BSAVE` → Arduino → **ブラウザ** → `capture.bin`
3. ブラウザ → エミュレータ `BLOAD` → エミュレータ `BSAVE`
4. → ブラウザ → Arduino `LOAD`+`PLAY` → 実機 `NEW` + `BLOAD`
5. 実機 `BSAVE` → Arduino → ブラウザ → `capture(1).bin`

**4 種類の波形生成・復号（実機の ROM、エミュレータの JS、Arduino の送出、
Arduino の取り込み）を経ても 1 バイトも変わらなかった。**
エミュレータと実機ではクロックが 9/8 違う（実機 8.00 MHz、エミュレータの
既定 9000 kHz）が、`.bin` はタイミングに依存しない形式なので影響しない。

## 得られた知見

1. **`.bin` を唯一のやり取りの単位にしたのが効いた。**
   波形の知識をファームウェアに閉じ込めたので、ブラウザ側は 2 ファイル・
   エミュレータ本体の変更は 2 か所で済んだ。
2. **クロックの違いは `.bin` に現れない。** 実機とエミュレータで
   9/8 の差があるが、往復しても内容は変わらない。
3. **`NEW` を挟んで確認する。** 実機の `BLOAD` は上書きなので、
   `NEW` せずに `LIST` が出ても「元から入っていた」可能性が消えない。
4. **既存の経路を必ず確認する。** リファクタした `bloadLoadFile()` と
   分岐を足した `bsaveFinish()` は、実機を使わない側も通しておく。
