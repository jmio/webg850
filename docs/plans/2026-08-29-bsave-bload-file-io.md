# 解析計画: BSAVE / BLOAD をブラウザ経由のファイル入出力に橋渡しする

作成日: 2026-08-29
状態: フェーズ 4 まで完了、フェーズ 5 は一部（2026-08-29 更新）

## 目的

内蔵 BASIC の `BSAVE` コマンドの動作を追跡し、実機では 11pin インターフェース（カセット／
シリアル）へ出力される BASIC プログラムの内容を、エミュレータ側の I/O 層でトラップして
ブラウザからファイルとして取り出せるようにする。

さらにその逆として、ブラウザから読み込んだファイルの内容をエミュレータの入力ポートへ
流し込み、`BLOAD` コマンドでエミュレータ内の BASIC に戻せるようにする。

## ゴール（完了条件）

1. エミュレータ上の BASIC で `BSAVE` を実行すると、その内容がファイルとしてダウンロードされる。
2. 1 で取り出したファイルをブラウザから読み込ませた状態で `BLOAD` を実行すると、
   保存時と同じ内容が BASIC 側に復元される。
3. 1 → 2 の往復で内容が完全に一致する（バイト単位で比較）。
4. 取り出したファイルの形式（実機の記録形式そのままか、独自形式か）が文書化されている。
5. 上記 1〜3 が **Firefox + `file://` の従来手順**（[README.md](../../README.md)）でも成立する。

## 実行環境

解析中は自動操作しやすい環境を使い、**最終的な動作は Firefox + `file://` で保証する**。

### 解析中（作業効率を優先する）

- リポジトリ直下をローカル HTTP サーバで配信し（例: `python -m http.server`）、
  `http://localhost:8000/webg850v.htm` を開く。
  Firefox が必要な理由は `rom.zip` / `ram.txt` を XHR で読むための
  `security.fileuri.strict_origin_policy` だけなので、`file://` をやめれば
  この制約が消え、ブラウザを選ばずに動かせる。
  - 要確認: 同期 XHR と `overrideMimeType("text/plain; charset=x-user-defined")` が
    HTTP 経由でも同じ挙動になること。着手時に最初に確認する。
- ブラウザ操作は Playwright から行う。このエミュレータは関数がすべてグローバルなので、
  UI を経由せず JavaScript から直接呼べる。
  - キー入力: `buttonHold(gkey)` / `buttonRelease(gkey)`
  - 状態確認: `disasm()` / `memdump()` / `z80read8()` / `z80debug_log()`
  - 出力回収: `console.log` は `#TEXT_CONSOLE` に溜まるので、その `value` を読む
  - 画面確認: LCD は canvas なのでスクリーンショットで見る（DOM を読んでも何も分からない）
- **トレースの差し込みはファイルを書き換えずに行う。** グローバル関数を実行時にラップする。

  ```js
  var _out18 = out18;
  out18 = function(x) { trace.push([states(), x]); _out18(x); };
  ```

  これでフェーズ 0〜1 は `g800main.js` に触れずに進められる。規則が確定してから正式にコードへ入れる。
- **測定データはブラウザ内で集計してから取り出す。** BSAVE 1 回で `out18` の呼び出しは
  数万件になるため、エッジ間隔のヒストグラムなどに畳んでから読み出す。
  生データが必要なときはファイルとして `docs/binary/` へ落とす。

### 最終形が満たすこと（Firefox + `file://`）

| 項目 | 制約 |
|:--|:--|
| ファイル読み込み | `fetch()` は `file://` で使えない。既存と同じ `XMLHttpRequest` を使う |
| ファイル書き出し | `createObjectURL` + `a.click()`（既存 `downloadData()` と同じ方式。RAMSAVE で実績あり）|
| ファイル選択 | `FileReader`（既存 `loadData()` と同じ）|
| 構文・API | 特定のブラウザでしか通らないものを使わない。既存コードの範囲に留める |
| 検証 | フェーズ 5 の往復試験は **Firefox + `file://` でも実施する**。HTTP 配信での成功だけで完了としない |

## 現状の把握（コードから確認済みの事実）

### 出力側

- 11pin インターフェースの出力制御は I/O ポート `0x18`。[g800main.js:963](../../g800main.js#L963) `out18(x)`。
- `out18` は 2 つの役割を持つ。
  - ブザー波形の生成（`x & 0xc0` を見て `wave` を書き換える）
  - `serialcapture(x)` の呼び出し（[g800main.js:930](../../g800main.js#L930)）
- 既存の `serialcapture()` は **ソフトウェア UART のデコーダ**として書かれている。
  - `x & 0x02` が真のときだけ処理する（ゲート）
  - データビットは `x & 0x80` の**反転**（`(x & 0x80) ? 0 : 1`）
  - スタートビット → 8 ビット（LSB ファースト）→ 文字として `console.log` に出力
  - **ビット幅（ボーレート）を一切見ておらず、`out18` が呼ばれた回数で数えている。**
    そのため実機のタイミングと合っている保証がなく、そのままでは BSAVE の解析に使えない可能性が高い。
- `in18()` は未対応（常に 0）。

### 入力側

- 11pin インターフェースの入力は I/O ポート `0x1F`。[g800main.js:1047](../../g800main.js#L1047) `in1f()`。

  ```js
  return keyBreak | (siocapture == true ? 0x02 : 0x00);
  ```

  - bit7 (`0x80`) は BREAK キーの状態（`keyBreak`）
  - bit1 (`0x02`) が 11pin の入力データ線に相当する
  - `siocapture` は [g800main.js:450](../../g800main.js#L450) で `false` に初期化されたきり
    **どこからも書き換えられていない**。つまり入力経路は事実上のスタブであり、ここが
    BLOAD 用データを注入する差し込み口になる。

### タイミングを測る手段

- 1 フレームで実行する Z80 ステート数は `clocks / (fps * fpsN)`。G850 既定では 9,000,000 / 60 = 150,000 ステート。
- `z80executeStates`（そのフレームで実行する総ステート数）と `z80restStates`（残り）から、
  フレーム内の経過ステート数 = `z80executeStates - z80restStates` が求まる。
  既存のブザー処理（`out18`）が波形位置の算出に同じ計算を使っている。
- ただし**フレームをまたいで連続する絶対時刻のカウンタは存在しない。** ビット幅の計測には
  累積ステートカウンタを新設する必要がある。

### その他の前提

- 実機 ROM をロードしているため `z80subroutine()` は無効（`romBanks > 0` で即 `-1` を返す）。
  BSAVE は ROM 内の実コードが動くので、**IOCS フックではなく I/O ポート層でトラップする**のが妥当。
- ファイルの出し入れには既存の `downloadData(content, filename, mimetype)`
  （[g800main.js:4014](../../g800main.js#L4014)）と `loadData()`（[g800main.js:4037](../../g800main.js#L4037)）が使える。
  ただし `loadData()` は Intel HEX 専用に書かれているため、バイナリを扱うなら
  `readAsArrayBuffer` を使う別関数が必要。

## 未確定事項

外部資料（[docs/bsave-format.md](../bsave-format.md) の出典）と実測により、Q1〜Q3 は解決した。

| # | 調べること | 状況 |
|:--|:--|:--|
| Q1 | `BSAVE` は 11pin へどの変調方式で出力するか | **解決**: XOUT の PWM。H 期間の長短で 0/1 を表す。ポート `0x18` の **bit7 のみ**を使う |
| Q2 | 1 ビットあたりの時間、ビット順・極性 | **解決**: エミュレータ実測で 0 = H 145usec、1 = H 360usec（実機は 162 / 406usec）|
| Q3 | ファイル全体のフレーム構成 | **解決**: PULSES1 → PWM1 → PULSES2 → PWM2 → PULSES3。詳細は [docs/bsave-format.md](../bsave-format.md) |
| Q4 | `BSAVE` に装置指定があり、指定によって出力先や形式が変わるか | 未確認。引数なしでも転送は始まる |
| Q5 | `BLOAD` 側が入力を読むポート | **解決**: `0x1F` の **bit2(0x04)**。bit1 ではない |
| Q6 | `BLOAD` が要求する入力タイミング | **解決**: 約 3usec 間隔でポーリングしており、BSAVE と同じ波形を返せば通る |
| Q7 | ハンドシェイクの有無 | ほぼ不要と判明。`BSAVE` は相手の応答を待たずに送出する |
| Q8 | PWM_DATA1 の 48 バイトの詳細とパリティの再現 | 未確認（新規）|

**注意**: 転送は十数秒〜20 秒以上かかる。観測窓が短いと「何も出ていない」と誤認する。

## 手順

### フェーズ 0: 計測基盤の用意

- 累積 Z80 ステートカウンタを追加する（フレームをまたいで単調増加する値）。
- `out18` に入った値と、そのときの累積ステートを記録するトレースバッファを追加する。
  出力は既存のデバッグ窓（`console.log`）ではなく、後でまとめてダンプできる配列に溜める。
  毎回 `console.log` すると文字列連結で重くなるため。
- トレースの ON/OFF を切り替える UI（チェックボックス）を `webg850v.htm` に追加する。

完了条件: BASIC を操作している間の `out18` の書き込みが、値と時刻の対で取り出せる。

**済**（2026-08-29）。`run` と `out18` の実行時ラップで実現。`g800main.js` は未変更。
操作手順は [docs/debug-operation.md](../debug-operation.md) を参照。

### フェーズ 1: BSAVE の出力を観測する

- 短く内容の分かっている BASIC プログラム（例: 1 行だけ）を用意して `BSAVE` を実行し、
  フェーズ 0 のトレースを取得する。
- 立ち上がり／立ち下がりの間隔をヒストグラムにして、Q1・Q2 を判定する。
  - 間隔が 1 種類＋その整数倍 → 非同期シリアル
  - 2 種類の周期が交互 → FSK（カセット形式）
- 判明した規則で手作業でデコードし、既知のプログラム内容と突き合わせて Q3 を詰める。
- `BSAVE` の装置指定を変えて出力が変わるかを確認する（Q4）。

完了条件: 出力ビット列 → バイト列への変換規則が書き下せる状態。結果は
`docs/` 直下の解析ドキュメントに残す。

**一部済**（2026-08-29）。パルス幅と全体構造は [docs/bsave-format.md](../bsave-format.md) に記録した。
残りは PWM_DATA1 の詳細とパリティの再現（Q8）、および装置指定の確認（Q4）。

### フェーズ 2: 出力トラップとファイル書き出しの実装

- フェーズ 1 で得た規則に沿ったデコーダを実装する。既存の `serialcapture()` は
  ビット幅を見ていないので、**置き換えるか、別関数として並置する**（既存の
  シリアル文字表示の用途を壊さないよう注意）。
- デコード結果をバッファに溜め、転送終了（終端検出、または一定時間の無通信）を
  トリガに `downloadData()` を呼ぶ。
- 保存形式を決める。第一候補は**デコード後の生バイト列をそのまま保存**（実機のファイル内容に相当）。
  ヘッダ情報を残すかどうかはフェーズ 1 の結果を見て決める。

完了条件: `BSAVE` 実行でファイルがダウンロードされ、内容が期待通り。

**済**（2026-08-29）。保存形式は PWM1 の 48 バイト + PWM2 のメインデータ。
`10 REM UUUU` で 70 バイトのファイルを得て、パリティも照合できた。
詳細は [docs/bsave-format.md](../bsave-format.md)。

### フェーズ 3: BLOAD の入力経路を調べる

- `BLOAD` を実行し、`in1f`（と念のため `in18`）が**いつ・どれだけの頻度で読まれるか**をトレースする。
  ポーリング間隔から Q6（許容タイミング）の当たりを付ける。
- 入力が来ないまま `BLOAD` がどう振る舞うか（タイムアウト、エラー番号）を観察し、
  成功判定の条件を推定する。
- `out18` の他ビットが入力中に変化するかを見て、ハンドシェイクの有無を確認する（Q7）。

完了条件: 「どのポートの、どのビットを、どのタイミングで変化させれば `BLOAD` が読むか」が分かる。

**済**（2026-08-29）。ポート `0x1F` の bit2。

### フェーズ 4: 入力インジェクタの実装

- ファイル読み込み用の関数を追加する（`loadData()` を参考に `readAsArrayBuffer` 版）。
- 読み込んだバイト列をフェーズ 1 の規則でビット列へエンコードし、
  「累積ステート数 → データ線の値」を返す形で保持する。
- `in1f()` を変更し、注入が有効なときは bit1 をその値にする。
  **`keyBreak`（bit7）は必ず保持すること。** BREAK キーが効かなくなる。
- 送出開始／中断の UI を `webg850v.htm` に追加する。

完了条件: ファイルを読み込ませて `BLOAD` すると成功する。

**済**（2026-08-29）。LOAD BIN ボタンから実ファイルを読み込み、`BLOAD` で復元できた。

### フェーズ 5: 往復試験

- 複数のプログラム（短い／長い、行数が多い、特殊文字を含む）で BSAVE → BLOAD の往復を行い、
  `LIST` の内容とメモリ内容（`memdump`）が一致することを確認する。
- 長いプログラムでフレーム境界をまたぐケースを必ず含める。フェーズ 0 の累積カウンタが
  正しく効いているかの検証になる。
**進捗**（2026-08-29）: `10 REM UUUU` の 1 本だけ往復確認済み。残りは以下。

- **仕上げに Firefox + `file://` の従来手順で同じ往復試験を通す。** 解析中に使っていた
  HTTP 配信では `file://` 固有の制約が隠れるため、ここを省略しない。

## 注意

- **ROM の内容をコミットするドキュメントに貼らないこと。** BSAVE の処理を ROM 逆アセンブルで
  追う場面が出てくるが、その**解析経過は `docs/binary/` 以下（追跡対象外）に書く**。
  コミットするドキュメントに残すのはアドレスと役割の対応、レジスタの使われ方、処理の流れの説明に留める。
  取り出した BASIC プログラムは利用者自身が書いたものなので扱いは自由。
- 既存の `serialcapture()` によるシリアル文字表示は別用途で使われている可能性がある。
  置き換える場合は挙動が変わることを明示する。
- ビット幅が実機と合っていないと `BLOAD` は失敗する。フェーズ 1 の計測を省略して
  推測でエンコーダを書かないこと。
