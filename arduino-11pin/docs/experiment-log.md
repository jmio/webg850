## 2026-08-30 ボード単体での確認（ジャンパなし・実機なし）

Arduino Uno R4 Minima を USB で接続。**COM16**（`VID_2341` / `PID_0069`）。
`pio run -t upload --upload-port COM16` で DFU 書き込み成功。

Bluetooth の COM ポートが 6 本見えている環境なので、**`--upload-port` と `-p` は
必ず明示する。** 自動検出だと外す。

### 割り込み対応ピンの確認

Renesas コアのピンテーブル
（`framework-arduinorenesas-uno/variants/MINIMA/pinmux.inc` と `variant.cpp`）を確認した。

| Arduino | ポート | 割り込み |
|:--|:--|:--|
| **D2** | P105 | **`PIN_INTERRUPT\|CHANNEL_0`** ✅ |
| D3 | P104 | `PIN_INTERRUPT\|CHANNEL_1` |
| D4 | P103 | **なし** |
| D5 | P102 | **なし** |

D2 を XOUT の取り込みに割り当てた判断は正しい。D4 / D5 は割り込みを持たないが、
単なる入力／出力としてしか使わないので支障ない。

### 起動直後の状態

```
+PONG g850-11pin 0.1.0
+INFO pins xout=D2 xin=D3 busy=D4 ack=D5
+INFO bincap=12288 rawcap=3072 binlen=0 xin=Z
+PINS xout=0 busy=0 ack=0 xin=Z
```

**`xin=Z`**。起動直後は D3 を入力にしてあるので、実機側の線を一切駆動しない。
段階 0 の安全確認の前提が成り立っている。

### DECTEST（ビット列の組み立て → 復号の往復）

```
python host/g850ctl.py -p COM16 dectest ../tools/tmp/bsave-test.bin
python host/g850ctl.py -p COM16 dectest ../tools/tmp/basen.bin
```

| 対象 | ブロック | len | got | bad | fe | hdr | parity | calc | 判定 |
|:--|:--|--:|--:|--:|--:|:--|:--|:--|:--|
| `bsave-test.bin`（70B）| PWM1 | 48 | 48 | 0 | 0 | 10000/40/40 | `0018` | `0018` | OK |
| | PWM2 | 22 | 22 | 0 | 0 | 25848/20/20 | `002D` | `002D` | OK |
| `basen.bin`（2854B）| PWM1 | 48 | 48 | 0 | 0 | 10000/40/40 | `001D` | `001D` | OK |
| | PWM2 | 2806 | 2806 | 0 | 0 | 25848/20/20 | `2304` | `2304` | OK |

**デバイス側・ホスト側とも PASS。**

意味のあるところ:

- `bad=0` — 復号したバイト列が元と 1 バイトも違わない
- `fe=0` — 9 ビット 1 組のスタートビットが全部 1 だった（ビット位置がずれていない）
- `hdr` — ヘッダのビット数が送出時の設定どおりに読み戻せた
- パリティが**既存ドキュメントに記録済みの値**（`0018` / `002D` / `001D` / `2304`）と一致
- **ファームウェア（C++）とホスト（Python）の独立した 2 実装が同じ値を出した**

### ASCII 16 進の往復（LOAD → DUMP）

`basen.bin`（2854 バイト）を `LOAD` した状態で `DUMP` し、元ファイルと照合。

```
ROUNDTRIP: 2854 バイト完全一致
```

`LOAD` 時の CRC16 は `5576`、`DUMP` 時も `5576`。転送形式（`D <offset> <hex>`）が
双方向とも正しく働いている。

### 副産物: シリアルポートを開き直してもボードはリセットされない

`dectest` で `LOAD` した内容が、**接続を張り直したあとの `dump` でそのまま
読み出せた。** つまり Uno R4 Minima は USB CDC を開いただけではリセットされない
（1200bps タッチのときだけブートローダに入る）。

コマンドを別々のプロセスに分けて実行してもバッファやタイミング設定は残る。
ただし依存させると壊れやすいので、`dectest` / `selftest` は 1 接続の中で
`LOAD` まで済ませる作りのままにしておく。

## 2026-08-30 SELFTEST（D3→D2 ループバック・実機なし）

D3 と D2 を **100Ω** を介して接続。D2 は高インピーダンス入力なので電圧降下も
時定数（ピン容量 10pF として約 1ns）も無視できる。実機は接続していない。

### 短縮タイミング（`PROFILE FAST`、70 バイトの `.bin`）

```
DONE edges=17588 long=9 longover=0 span_us=3479783
H: 最頻 174 usec / 8577 個   最頻 419 usec / 213 個
L: 最頻 176 usec / 8567 個   最頻 421 usec / 210 個
   （ほかに 481 usec × 6、725 usec × 5）
```

### 実機相当タイミング（`PROFILE REAL`、同じ `.bin`）

```
DONE edges=73284 long=9 longover=0 span_us=27114094
H: 最頻 174 usec / 36425 個   最頻 419 usec / 213 個
L: 最頻 176 usec / 36382 個   最頻 421 usec / 241 個
```

### ビット数がエミュレータの実測と完全一致した

| | Arduino の送出（本実験）| エミュレータが実機 BSAVE を取り込んだ実測 |
|:--|--:|--:|
| H 短（ビット 0）の個数 | **36425** | **36425** |
| H 長（ビット 1）の個数 | **213** | **213** |
| エッジ数 | 73284 | 73285 |
| 区切りの長い H | 4 回 | 4 回 |

出典は [../../docs/analysis/bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md)
の「パルス幅」の表。**同じ `.bin` から組み立てたビット列が、ROM が出す
ビット列と 1 個も違わない構成になっている。**

内訳の検算も合う。

- 総ビット数 = PWM1 10532 + PWM2 26106 = **36638** = 36425 + 213
- 1 の個数 = ヘッダの 1（40 + 20）+ START/STOP（2 × 2）
  + 各バイトのスタートビット（50 + 24 = 74）
  + データ中の 1（PWM1 24 + パリティ 2、PWM2 45 + パリティ 4）= **213**
- エッジ数 = 36638 × 2 + 区切り 4 × 2 = **73284**

### PULSES の順序と長さ

`L <番号> <レベル> <usec>` の 9 本が、資料の構成そのままに並んだ。

| # | レベル | 実測 (REAL) | 設定 | 対応 |
|--:|:--|--:|--:|:--|
| 0 | H | 30011 | 30000 | PULSES1 の区切り |
| 1 | L | 8000014 | 8000000 | PULSES1 の L |
| 2 | L | 2000425 | 2000000 | PULSES2 の L |
| 3 | H | 30012 | 30000 | PULSES2 の区切り |
| 4 | L | 24012 | 24000 | PULSES2 の中間 L |
| 5 | H | 30012 | 30000 | PULSES2 の区切り |
| 6 | L | 6014 | 6000 | PULSES2 の最後の L |
| 7 | L | 4000422 | 4000000 | PULSES3 の L |
| 8 | H | 30018 | 30000 | PULSES3 の区切り |

`#2` と `#7` だけ +425 とずれるが、これは**誤差ではない**。
PWM ブロックの最後の STOP_BIT（ビット 1）の L 側 411usec が、
続く PULSES の L と地続きになって 1 本の区間として観測されるため。
2000000 + 411 + 14 ≒ 2000425 で説明がつく。
`#1`（前がビットでなく区切りの H）は +14 しかずれていないことが裏付けになる。

### 誤差は「一定の上乗せ」であってスケール誤差ではない

| 設定 [usec] | 実測 [usec] | 差 |
|--:|--:|--:|
| 162 | 174 | +12 |
| 406 | 419 | +13 |
| 6000 | 6014 | +14 |
| 24000 | 24012 | +12 |
| 30000 | 30011〜30018 | +11〜+18 |
| 8000000 | 8000014 | +14 |

**5 桁にわたって差が +13usec 前後で一定。** 比例していないので
時間軸のスケール誤差ではなく、**1 区間あたりの固定オーバヘッド**である。
内訳は「割り込みハンドラの実行時間 + `digitalWrite` + `micros()` の呼び出し」。

重要な点:

- **この +13usec は SELFTEST でしか乗らない。** 通常の `PLAY` では取り込みの
  割り込みを張っていないので、残るのは `digitalWrite` + ループの数 usec だけ。
- **`CAP` の測定値には影響しない。** 立ち上がりと立ち下がりの両方に同じ
  割り込み遅延が乗るので、幅を取るときに相殺される。実機の波形を測るときは
  正確な値が出る。
- 補正は入れない。判定しきい値は 162 と 406 の中間（284usec）で、
  174 との差は 110usec もある。13usec の上乗せは問題にならない。
- **Uno R4 Minima の `micros()` に系統的なスケール誤差は無い**と言える。
  もしあれば 8000000usec の区間で数千 usec ずれるはずだが、+14usec だった。

所要時間は REAL で 27.11 秒。上乗せ分（36638 ビット × 2 区間 × 13usec ≒ 0.95 秒）を
引くと 26.1 秒で、エミュレータの実測 23.34 秒 × 9/8 = 26.3 秒という推定と合う。

### L 側に現れる 480 / 700 usec 台の区間について

進捗表示（`*PLAY ...`）を 300ms ごとに出しており、これが 1 回あたり
**約 300usec** かかる。書き込みは L を出し終えた直後に行うので、
その分だけ L が伸びて別のかたまりとして現れる。

**H には一切現れていない**（H は 173-175 と 417-420 の 2 群だけ）。
「ビットの値は H の長さだけで決まり、L の長さは見られていない」という
前提のもとで、意図どおり L 側へ逃がせていることの確認になる。

### 判定

**SELFTEST 合格。** 組み立てたビット列も、パルス幅も、PULSES の構成も
意図どおり電気信号として出ている。

実機で残る不確かさは **タイミングの絶対値**（実機が 162/406usec で
出しているのか）と **極性** の 2 つだけに絞られた。

## 段階 0: 配線とレベルの確認（2026-08-30・完了）

### 配線

```
  PC-G850                        ブレッドボード         Arduino
  pin-3 GND ────────────────────────────────────────── GND
  pin-7 XOUT ──[100Ω]──┬───────────────────────────── D2
                        │
                       ═╪═ 100nF (104)
                        │
                       GND
```

pin-2 (VCC) は未接続。pin-6 (XIN) はこの段階では未接続。
pin-4 (BUSY) を一度 D4 につないだが、配線を減らすため取り外した。

### 実測

| 確認項目 | 期待 | 実測 | 判定 |
|:--|:--|:--|:--|
| ピン番号の向き | 左端が pin-1 | pin-2/pin-3 間が **+5V** | **確定** |
| XOUT (pin-7) のアイドル電圧 | 0V 付近 | **0V 付近** | OK |
| `BSAVE` 中の XOUT（PWM 区間の平均）| 2.5V | **2.46V** → H = **4.92V** | **5V 系で確定** |
| `PINS` の `xout` | 0 | **0**（5 回とも安定）| OK |
| `RAW` でエッジが見えるか | 見える | 見える | OK |

**PWM 区間のデューティが正確に 50% であることを利用して、DC 電圧計の平均値読みから
H レベルを求めた。** 各ビットが「H を t、続けて L を t」なので 0 でも 1 でも
H:L = 1:1 になる。テスターしか無くても振幅が測れる。

### 極性の確定

想定（アイドル = 論理 1 = LOW = 0V）が実測で裏付けられた。4 つの根拠が一致。

| 根拠 | 内容 |
|:--|:--|
| 資料の表 | 論理 1 (Mark, Idle, Stop) = LOW = 0V |
| エミュレータ実測 | SIO のアイドル（論理 1）のとき `0x18` bit7 = 0 |
| I/O 資料 | `18H` は「0 = L 出力、1 = H 出力」 |
| **今回の実測** | **pin-7 のアイドル = 0V、`RAW` の先頭が H（区切り）から始まる** |

`invin` / `invout` はどちらも **0（反転なし）**でよい。

### RAW による構造の確認

```
 0  H      30022 us   ← PULSES1 の区切り
 1  L    7965385 us   ← PULSES1 の L（約 8 秒）
 2  H        161 us   ← PWM1 ヘッダの 0 が始まる
 3  L        165 us
 4  H        161 us   … 以降 1535 ビット分
```

| 測定 | 実測 | 推定値 | 差 |
|:--|--:|--:|--:|
| 区切りの H | 30022 µs | 30000 | +0.07% |
| PULSES1 の L | 7,965,385 µs | 8,000,000 | −0.43% |
| ビット 0 の H | 161.8 µs（最頻 162、範囲 159–165）| 162 | ±0.1% |
| ビット 0 の L | 164.0 µs（最頻 164、範囲 161–167）| 162 | +1.2% |

**H(161.8) より L(164.0) が約 2µs 長い。** ROM のビットバンギングのループが
左右非対称ということ。受信側は H の長さしか見ないので復号には影響しない。

`RAW` はエッジを 3072 本しか保持できないので、PWM1 のヘッダの 0 の並びで
埋まって止まる。**構造と極性の確認には十分だが、ビット 1（406µs）は捉えられない。**
幅の統計は `CAL` の担当。

## 段階 1: 時間軸の較正 (CAL)（2026-08-30・完了）

対象プログラム: `10 REM UUUU` の 1 行のみ（`NEW` 後に入力）。

### エミュレータとの比 — 9/8 換算が正しかった

| 定数 | 実機 | エミュレータ実測 | 比 | 9/8 = 1.125 か |
|:--|--:|--:|--:|:--|
| `bit0` | **162** µs | 145 µs | 1.117 | **一致** |

| `mark` | **30021** µs | 27000 µs | 1.112 | **一致** |
| 転送全体 | **26.16** 秒 | 23.34 秒 | 1.121 | **一致** |

**4 つの独立した量がすべて 1.11〜1.13 に収まった。** エミュレータの既定クロック
9000 kHz に対し、**実機の実効クロックは 8.00 MHz** と確定してよい。
ポート `67H` の 4MHz 側（比が 2.25 になるはず）では動いていない。

これで [../../docs/analysis/bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md) の
「エミュレータのクロックは実機より約 11% 速い」という推定が**実機で裏付けられた。**

### 採用した設定値

```

p1l=7965382  p2l=2008226  p2s1=23969  p2s2=6013  p3l=3998066
```

保存した結果は記録として
[cal-2026-08-30-pc-g850v.json](cal-2026-08-30-pc-g850v.json) に残してある
（この表と下の外れ値の一覧は、そこから丸めて作ったもの）。

この時点では**ボードは書き込みや電源断で既定値に戻る**ので、

のちに v0.2.0 でこれらの値を既定値として焼き込んだため、現在は不要。

## 段階 2: 取り込みと復号 (CAP)（2026-08-30・完了）

### 1 回目 — 失敗。原因を特定

```
R 1 bytes=50 data=48 hdr=9998/40/40      parity=0018 calc=0018 OK fe=0
R 2 bytes=28 data=26 hdr=12645/1/13193   parity=B012 calc=004D NG fe=20
DONE marks=4 bits=36627 blocks=2 glitch=3 ovf=0 ms=26134 status=ok
```

- **PWM1 は完全に成功。** 48 バイトが `bsave-test.bin` の先頭 48 バイトと
  **バイト単位で一致**した（パリティ `0018` も一致）。
- **PWM2 が失敗。** ヘッダの読み飛ばしが `12645 個の 0 → 1 個の 1 → 13193 個の 0`
  で終わっている。本来 25848 個続く 0 の並びの**途中に 1 が 1 個紛れ込んだ**形。
  段階 1 で見つかった外れ値（338µs / 536µs）がこれ。

その結果、復号器は**本物の 20 個の 1 の並びの先頭を START_BIT と誤認**し、
9 ビットの枠が 1 ビットずれた。壊れた本体を見ると症状が明確に出ている。

```
実機(壊): ffff00003ff010701010101010101010101050ffd535b5b5b5b0
正しい  : ff0003000000000000000000000a07fe59555555550d
```

`1010101010…` は各バイトのスタートビットがデータ側に食い込んだ形。
**ビット自体は正しく取れていて、枠だけがずれている**（`fe=20` が 20 個の 1 に対応）。

### 打った対策

| # | 対策 | 内容 |
|:--|:--|:--|
| 1 | **ファームウェア** | ヘッダの「1 の並び」として認める最低長を `PWM_MIN_ONES = 5` とし、それ未満の孤立した 1 はノイズとして 0 の並びに戻す。実機のヘッダは 1 が 20 個ないし 40 個続くので 4 倍の余裕がある |
| 2 | **配線** | D2 と GND の間に **100nF (104)** を追加。既存の 100Ω 直列と合わせて時定数 10µs の LPF になる。162µs のパルスの 1/16 なので波形は保たれ、両エッジが同じだけ遅れるので幅も変わらない |

対策 1 は Python の参照実装にも同じ値で入れ、**実際に壊れた位置（12645 ビット目）
への 1 個注入で完全復号できること**、4 個連続まで吸収し 5 個以上は本物の
ヘッダとみなすことを確認してから実機に適用した。

### 2 回目 — 成功

```
R 1 bytes=50 data=48 hdr=9998/40/40  parity=0018 calc=0018 OK fe=0 noise=0
R 2 bytes=24 data=22 hdr=25844/20/20 parity=002D calc=002D OK fe=0 noise=1
DONE marks=4 bits=36632 blocks=2 glitch=0 ovf=0 ms=26134 status=ok

>>> bsave-test.bin と 70 バイト完全一致
```

| # | 成功条件 | 結果 |
|:--|:--|:--|
| 1 | 区切り 4 回で正常終了 | `marks=4 status=ok` |
| 2 | PWM1 が 48 バイト + パリティ一致 | `data=48 parity=0018 calc=0018 OK` |
| 3 | 申告サイズと実バイト数が一致 | `declared=22 body=22` |
| 4 | PWM2 のパリティ一致 | `parity=002D calc=002D OK` |
| 5 | **エミュレータの `.bin` と一致** | **70 バイト完全一致** |

**実機とエミュレータのファイル互換が証明された。**
ヘッダの「謎の 4 バイト」を含め、48 バイトすべてが一致している。

### どちらの対策が効いたかの切り分け

| 指標 | 1 回目 | 2 回目 | 意味 |
|:--|--:|--:|:--|
| `glitch` | 3 | **0** | **104 のコンデンサが 40µs 未満の短いスパイクを消した** |
| `noise` | （機能なし → 失敗）| **1** | **長い外れパルスは残っており、ファームウェアの保護が吸収した** |

**両方が必要だった。** コンデンサだけでは 338/536µs の長い外れパルスが残り、
保護が無ければ 2 回目も失敗していた。

`hdr` が本来の 10000 / 25848 に対して 9998 / 25844 と数個少ないが、
**ヘッダの 0 の並びの中での取りこぼしなので無害**（復号器は 1 が来るまで数えるだけ）。
`fe=0` で枠ずれなし、`ovf=0` で取りこぼしなし。

## 段階 3: 再生 (PLAY)（2026-08-30・完了）

### 配線の追加

```
  pin-6 XIN ──[1kΩ]────────────────── D3
```

1kΩ を選んだのは競合時の電流を 5mA に抑えるため（100Ω だと 50mA で
RA4M1 の絶対最大を超える）。XIN 側にはコンデンサを入れないので
時定数の問題は無く、大きめの抵抗にデメリットが無い。

`IDLE 1` で駆動して pin-6 を測ると **4.8V**。1kΩ でも駆動は十分で、
実機側に低い値のプルダウンは無いことが分かった。

### 送出したもの

段階 2 で取り込んだ 70 バイトの本体だけを書き換えた。

```
元 : ff0003000000000000000000000a07fe59 55555555 0d   (UUUU)
新 : ff0003000000000000000000000a07fe59 41424344 0d   (ABCD)
```

長さは 22 バイトのまま、PWM2 のパリティは `002D` → `0026`（送出時に自動計算）。

**実機には `10 REM UUUU` が入っていたので、同じ内容を送ると
「転送されたのか `NEW` の消し残しを拾ったのか」が区別できない。**
エミュレータ側の実験で実際に踏んだ罠なので、目印を変えた。

### 1 回目 — 失敗。ただし極めて有益な症状

`invout=0`（反転なし）で送出。

| 観測 | 内容 |
|:--|:--|
| 実機 | `BLOAD` の待ち状態から抜けない。エラーは出ない |
| ブザー | **複数回、数秒〜10 秒程度鳴った** |
| BREAK | エラーなく抜けた |

**ブザーの鳴り方が送出したデータブロックの長さと一致した。**

| ブロック | ビット数 | 送出時間 |
|:--|--:|--:|
| PWM1 | 10532 | 約 3.4 秒 |
| PWM2 | 26106 | 約 8.5 秒 |

カセットインタフェースのモニタ音と思われ、**信号は届いているが枠が
合っていない**ことを示していた。

### 2 回目 — 成功。XIN の極性が逆だと判明

`CFG invout 1` に変えて再送出。アイドル時の pin-6 は 4.8V（物理 H）になる。

```
DONE n=70 ms=26493 status=ok
```

実機は正常終了し、**`LIST` の結果が `10 REM ABCD`。**
元の `UUUU` ではないので、確実に転送されたものである。

### 確定した極性

| ポート | ビット | 11pin | 物理レベル | 向き |
|:--|:--|:--|:--|:--|
| `0x18` (out) | bit7 | pin-7 XOUT | **1 → 5V** | 非反転 |
| `0x1F` (in) | bit2 | pin-6 XIN | **1 ⟺ 0V** | **反転** |

**出力は非反転、入力は反転**という非対称な作り。
ファームウェアの既定を `invout=1` に変更した。

### なぜ推定では埋まらなかったか

**PWM 波形が対称（各ビットが「H を t、L を t」）だから。** 極性が反転しても
受信側が測る H 期間は送信側の L 期間になるだけで長さは同じ。
**ビットの値は正しく復号されてしまう**ので、狂うのは PULSES と区切りの解釈だけ。

- エミュレータの実装は証拠にならない（内部で閉じた往復なので極性が揃えば動く）
- 実機同士の転送も証拠にならない（同じ対称性で成立する）
- 外部資料のレベル表は SIO モードの記述で、入力バッファの反転までは書かれていない

**実機に信号を注入して初めて分かる性質だった。**
計画書 2.3 節に「XIN 側の極性は推定である」と書いて段階 0 と 3 で
検証対象に挙げていた項目に、そのとおり当たった。

### 往復試験（3-5）— 完全一致

`BLOAD` で書き込んだ内容を、そのまま実機の `BSAVE` で読み出して照合した。

```
R 1 bytes=50 data=48 hdr=9997/40/40  parity=0018 calc=0018 OK fe=0 noise=1
R 2 bytes=24 data=22 hdr=25844/20/20 parity=0026 calc=0026 OK fe=0 noise=0
DONE marks=4 bits=36631 blocks=2 glitch=0 ovf=0 ms=26130 status=ok

>>> play_abcd.bin と roundtrip.bin が 70 バイト完全一致
```

```
play_abcd.bin ──波形化──> 実機 BLOAD ──> RAM ──BSAVE──> 波形 ──復号──> roundtrip.bin
                                                                            │
                                                            70 バイト完全一致 ┘
```

**PWM2 のパリティが `0026`**（`ABCD` に対応。`UUUU` なら `002D`）。
実機の RAM から読み出された内容が確かに Arduino から送り込んだものである、
という `LIST` の目視とは独立した機械的な裏取りになった。

**「Arduino → 実機 → Arduino」が無損失であることが確定した。**

### 未実施

|:--|--:|--:|
| 22 バイト | 26.5 秒 | **3.33 秒** |

+ PULSES 0.29 秒 で、**ヘッダが支配的**。

### 失敗時の症状

**「待機のまま抜けない。エラーは出ない。画面右下のアスタリスクも出ない。」**

これは極性が逆だったとき（段階 3 の 1 回目）と同じ症状である。
どちらも実機が転送の開始を認識できていない状態で、区別がつかない。

| 症状 | 到達段階 |
|:--|:--|
| アスタリスクが出ない・待機のまま | **区切りの検出に失敗**（同期できていない）|
| アスタリスクが出る | 区切りが認識され、受信が進んでいる |
| `ERROR 80` | ビットまで読めたがパリティが合わない |

### アスタリスクは成功の指標として使える

画面右下のアスタリスクは、**成功した試行では出て、失敗した試行では出なかった。**
利用者によればエミュレータでも同じ表示が出る（ROM が受信の進行に応じて出している）。

**`LIST` を待たずに送出中に成否が分かる**ので、以降の切り分けはこれを見るのが速い。

### 注意: 各設定の試行は 1 回のみ

いずれの設定も **1 回しか試していない。** 再現性は確認していないので、
下限ぎりぎりの値（2000）を常用するのは避け、`PROFILE FAST` の 4000 を使うこと。

## 段階 A: 大きいデータの往復（2026-08-30・完了）

対象: `tools/tmp/basen.bin` 2854 バイト（ヘッダ 48 + 本体 **2806**）。
実際の BASIC プログラム（`*INIT` / `*MENU` などのラベルを持つ電卓風のもの）。
これまで試してきた 22 バイトの **128 倍**にあたる。

### 事前確認（実機不要）

| 確認 | 結果 |
|:--|:--|
| ホスト側参照実装の往復 | REAL / FAST とも OK（パリティ 001D / 2304）|
| ボード上の符号化・復号の往復 (`DECTEST`) | PASS（`bad=0 fe=0`、crc=5576）|

### 再生 (PLAY) — 1 回で成功

`BLOAD` で待たせてから `PLAY`。33846 ビットを **17.45 秒**で送出。

- 画面右下に `*` が出て待機から抜けた
- `LIST` で BASIC プログラムを確認
- **さらに `RUN` して正常に動作した**

**転送できただけでなく実行までできた**ので、実機のメモリ上で完全に正しい
プログラムになっていることが確かめられた。22 バイトのときより 128 倍
大きいデータでも、短縮タイミング (`PROFILE FAST`) はそのまま通用する。

### 取り込み (CAP) — 1 回目は失敗

```
R 1 bytes=50   data=48   hdr=9998/40/40     parity=001D calc=001D OK fe=0    noise=0
R 2 bytes=2804 data=2802 hdr=25841/20/20    parity=368E calc=2836 NG fe=1341 noise=2
DONE marks=4 bits=61656 blocks=2 glitch=3 ovf=0 ms=40050 status=ok
```

- **PWM1 は完全に成功**（48 バイトが元ファイルと一致、パリティも一致）
- **PWM2 が失敗。** 本体 2806 バイトのはずが 2802 バイト
- ヘッダの実測が `hdr1=9998`（−2）、`hdr2=25841`（−7）と**足りない**
- 総ビット数 61656 に対し理論値は 61694。**38 ビット足りない**

### 「実機側で壊れたのか、取り込みで壊れたのか」の切り分け

再生した直後にプログラムが動いたことからも取り込み側が疑わしいが、
それに頼らずに判定できる根拠が 2 つあった。

**根拠 1: フレーミングエラー `fe=1341` が出ている。**
実機は 9 ビットごとに必ず `1`（フレームビット）を置いて送る。
実機のメモリが壊れていたとしても、**送られるビット列の枠組み自体は正しい**
ので `fe` は 0 のまま、パリティだけが合わなくなるはずである。
枠が崩れているということは、受け取る途中でビット列そのものが変形した。

**根拠 2: ずれ方が「1 ビットの欠落」に完全に一致する。**
受信バイト列を送出ビット列に突き合わせて累積欠落ビット数を求めると、
値の誤りではなく**単純な欠落だけ**で全体を説明できた。

| 本体バイト位置 | 累積欠落 |
|--:|--:|
| 32 | 1 |
| 192 | 2 |
| 224 | 3 |
| 352 | 4 |
| 448 | 5 |
| 608 | 6 |
| 768 | 7 |

### 原因: 取り込み中のシリアル出力

**欠落位置がすべて 32 の倍数**である。32 / 192 / 224 / 352 / 448 / 608 / 768、
例外なし。当時の `capture.cpp` は

```c
static uint8_t s_line[32];
```

に 32 バイト貯まるたびに `+D` 行を USB へ流していた。つまり

> **取り込みの最中に USB へ書くと、その間にエッジ割り込みを取りこぼす。**

87 回の行送出のうち 7 回（約 8%）が当たった計算になる。
`hdr1` / `hdr2` の不足も同じ理由で、こちらは 1 秒ごとの `*CAP` 進捗行が原因。
ヘッダの 0 の並びは読み飛ばすだけなので実害が出ていなかった。

**`ovf=0` であることが効いている。** リングバッファは 256 本＝約 83 ms 分の
余裕があり、それが溢れていないということは、主ループが遅れていたのではなく
**エッジ割り込みそのものが発火していない**。したがってバッファを増やしても
復号を速くしても直らず、「書かない」以外に対策がない。

**22 バイトの転送では本体の `+D` が 1 回しか出ない**ので、これまでの実験では
一度も表面化しなかった。データが大きくなって初めて出る種類の不具合である。

### 修正 (v0.3.0)

| 変更 | 内容 |
|:--|:--|
| `capture.cpp` | 復号したバイトを `g_store`（12 KB）にためこみ、**転送が終わってから** `+D` / `+R` / `*MARK` をまとめて吐く |
| `capture.cpp` | 進捗 `*CAP` は最初の区切りを見る前だけ。転送中は完全に沈黙 |
| `capture.cpp` | `+DONE` に `dropped=` を追加。12 KB を超えたブロックは `+R` に ` TRUNCATED` が付く |
| `calib.cpp` | `CAL` の進捗も同じ理由で転送前だけに制限 |

**送出 (`PLAY`) 側は変更していない。** こちらは各区間の絶対時刻を再計算して
待つ設計なので、遅れは必ず L 側に吸収される。実際 2854 バイトの送出は
1 回で成功している。`RAW` はもともとエッジを貯めてから吐く作りなので変更不要。

### 取り込み (CAP) — 2 回目は完全成功

```
R 1 bytes=50   data=48   hdr=10000/40/40  parity=001D calc=001D OK fe=0 noise=0
R 2 bytes=2808 data=2806 hdr=25848/20/20  parity=2304 calc=2304 OK fe=0 noise=0
DONE marks=4 bits=61694 blocks=2 glitch=0 ovf=0 dropped=0 ms=40048 status=ok
```

| 項目 | 1 回目 (v0.2.0) | 2 回目 (v0.3.0) | 理論値 |
|:--|--:|--:|--:|
| `hdr1` | 9998 | **10000** | 10000 |
| `hdr2` | 25841 | **25848** | 25848 |
| 総ビット数 | 61656 | **61694** | **61694** |
| `fe` | 1341 | **0** | 0 |
| `noise` / `glitch` | 2 / 3 | **0 / 0** | 0 / 0 |
| 本体バイト数 | 2802 | **2806** | 2806 |

**ヘッダのビット数まで理論値と完全に一致した。1 ビットも落ちていない。**
`glitch=0` なので、100nF によるスパイク除去も効いたままである。

### 往復の検証

```
元ファイル   2854 バイト  sha256 26f3e7f18c1e...
取り込み結果 2854 バイト  sha256 26f3e7f18c1e...
完全一致: True
```

**PC → 実機 → PC の往復で 2854 バイトが 1 バイトも変わらずに戻ってきた。**

### 所要時間

| 向き | タイミング | 時間 |
|:--|:--|--:|
| 再生 (PLAY) | FAST | **17.45** 秒 |
| 取り込み (CAP) | 実機のまま | **40.05** 秒 |

取り込みが 2.3 倍かかるのは、実機が本来のヘッダ（10000 / 25848 ビット）と
長い PULSES（8 秒 + 2 秒 + 4 秒）をそのまま出すため。**取り込み側は短縮できない。**

### 副産物: 「表示が止まる」と「何も来ていない」が区別できなくなった

転送中に黙らせた結果、進捗の `CAP waiting Ns` が**最初の区切りを見た瞬間に
止まる**ようになった。ところがこれは「何も来ていない」ときの見え方と
区別がつかない。実際、修正直後の取り込みで `waiting 70s` のまま止まって
いるのを「まだ何も検出していない」と読み違え、実機で再度 `BSAVE` を
実行してもらった（そのときは既に受信中で、`ms=40048` で正常に完了していた）。

対策として、**最初の区切りの直後にだけ** `#cap begin mark=<幅>` を 1 回送る
ようにした。ここで喋ってよいのは、波形の構成上この直後に約 8 秒の L が
続くことが保証されているため（実測 7,965,382 µs）。他の区切りの後は
6〜24 ms しかないので同じことはできない。

ホスト側 (`g850ctl.py`) には `#` 行を受信時に表示するための `on_log` を
足し、取り込みでは「転送を検出。受信中は表示が止まります」と出す。

これで待ちの状態が 3 つに区別できる。

| 表示 | 意味 |
|:--|:--|
| `CAP waiting Ns` が増え続ける | まだ何も来ていない |
| 「転送を検出」が出て止まる | 受信中（実機のタイミングで約 40 秒）|
| `waiting` のまま止まる | 起きえない |

**沈黙させる設計には、沈黙が始まったことを知らせる仕組みが要る。**

### 残った制約: バッファの 12 KB では足りない

転送中に黙る修正で正しさは得られたが、**復号したバイトを全部 RAM に貯める**
という前提が残った。実機の空き容量は `PRINT FRE(0)` で **27286 バイト**。
一方バッファはどこまで増やせるか実測すると、

| バッファ | リンク結果 |
|--:|:--|
| 12288（当時）| OK — 静的領域 21484 |
| 13312 | OK — 静的領域 22508 |
| **13824** | **OK — 静的領域 23020（残り 532 バイト）** |
| 14336 | **失敗** `region RAM overflowed` |

RA4M1 の SRAM は 32768 バイトだが、リンカスクリプトが**ヒープ 8192 と
スタック 1024 を固定で確保**するため、静的領域に使えるのは 23552 バイト。
バッファ以外が 9196 バイトなので、**上限は 13.8 KB**。

**実機の空き容量のちょうど半分。増やす方向では解決しない。**
取り込みながらホストへ吐き出す以外に手が無い。

## 段階 B: 取りこぼしの原因を突き止める（2026-08-30・完了）

### 吐き出せる場所を数える

| 区間 | 長さ | 使えるか |
|:--|--:|:--|
| PULSES1 の L | 7.97 s | まだデータが無い |
| PULSES2 の L（PWM1 の直後）| 2.01 s | ブロック 1 の 50 バイトだけ |
| PULSES2 の中間 / 最後の L | 24.0 / 6.0 ms | 実質使えない |
| **PWM2 のビット間の L** | **164 µs**（ビット 0）/ 404 µs（ビット 1）| **ここしかない** |
| PULSES3 の L（PWM2 の直後）| 4.00 s | 全部吐けるが、その前に貯める必要がある |

帯域は足りている。1 ビットが 326 µs、9 ビットで 1 バイトなので 1 バイトあたり
2.93 ms。出力は 32 バイトの `D` 行が 74 文字なので**データ 1 バイトあたり
2.31 文字**、必要な送出速度は**毎秒 787 バイト**にすぎない。
L 期間 1 回あたり 0.26 バイト。1 回に 4 バイト吐ければ **15 倍の余裕**がある。

つまり**問題は帯域ではなく、書いている間にエッジを落とすかどうかだけ**。

### 割り込み優先度を調べる

`IRQ` コマンドを追加して NVIC の状態を見た。

```
+IRQ 0 event=33 prio=12   ┐
+IRQ 1 event=34 prio=12   │ USB FS（4 本使う）
+IRQ 2 event=31 prio=12   │
+IRQ 3 event=32 prio=12   ┘
+IRQ 4 event=1E prio=8      ← millis / micros のタイマ
+IRQ 5 event=..  prio=12    ← エッジ割り込み（attachInterrupt が設定）
```

**エッジ割り込みと USB がまったく同じ優先度 12。**

Cortex-M では**同一優先度の割り込みは互いに横取りできない**。USB の ISR が
実行中にエッジが来ても、USB が `return` するまでエッジ ISR は始まらない。
USB の ISR が 162 µs を超えれば、その間の H パルスは丸ごと失われる。

観測された現象と正確に一致する。

- リングバッファは溢れない（ISR が動いていないので push されない）→ `ovf=0`
- 落ちるのは 1 ビット単位
- 落ちる位置が行送出の瞬間

### 実験の仕掛け

| 設定 | 意味 |
|:--|:--|
| `CFG capstream 1` | 取り込み中に `+D` を吐く（既知の失敗パターン）|
| `CFG irqprio <0-15>` | エッジ割り込みの NVIC 優先度。255 で「触らない」|
| `IRQ` コマンド | 使用中の割り込みスロットとイベント番号・優先度を一覧 |
| `#cap irqn=<番号> prio=<値>` | `CAP` の冒頭に**実際に適用された値**を出す |

**この `#cap irqn=` を出す設計が実験を救った**（後述）。

### 実験 A（対照）: `capstream=1` / 優先度 12

```
DONE marks=4 bits=61676 blocks=2 glitch=1 ovf=0 ms=40048 status=ok
復元: 2852 バイト  declared=2806 body=2804  problems=size 2806!=2804
PWM2 パリティ 2304 / 計算 281A NG
```

理論値 61694 に対し **18 ビット不足**。`ovf=0` のまま消えるという特徴も同じ。
**新しいファームウェアでも不具合が確実に再現した。**

### 実験 B（1 回目・無効）: 検出バグ

`CFG irqprio 4` を設定して実行したが、結果は実験 A とほぼ同じ
（`bits=61677`）。「優先度では直らない」と結論しかけたところで
`#cap irqn=` の値を確認すると、

```
#cap irqn=-1 prio=255
```

**`-1` は「割り込み番号を検出できなかった」で、`NVIC_SetPriority` が
一度も呼ばれていなかった。**

`attachInterrupt` がどの ICU スロットを使うかは公開されていないので、
呼び出し前後で `R_ICU->IELSR[]` を比較して変化したスロットを探す方式に
していた。ところが、

- IELSR が変化するのは**起動後の最初の 1 回だけ**
- `detachInterrupt` を呼んでもスロットの内容は残る
- 2 回目以降の `attachInterrupt` は同じ値を書くので**差分が出ない**

書き込み直後に打った診断用の `CAP 3` が「最初の 1 回」を消費しており、
その後の実験 A・B ではずっと検出に失敗していた。
**一度見つけた番号を覚えておく**ようにして解決。

> **実際に適用された値を毎回報告させていなければ、
> 「優先度を上げても直らない」という誤った結論を出していた。**
> 設定した値ではなく、効いた値を出すこと。

### 実験 B（2 回目）: 優先度 4 — 別の壊れ方

```
R 1 bytes=0 hdr=777/0/0     R 2 bytes=0 hdr=751/0/0     R 3 bytes=0 hdr=530/0/0
DONE marks=4 bits=2058 blocks=3 glitch=0 ovf=0 ms=8637 status=ok
```

転送が **8.6 秒**で終わり、ブロックが 3 つでき、1 バイトも復号できなかった。

**優先度 4 は上げすぎだった。** `IRQ` の出力を読み直すと、

```
+IRQ 4 event=1E prio=8      ← millis / micros のタイマ
```

優先度 4 にすると**タイマ（優先度 8）まで横取りしてしまう**。
`micros()` はタイマ ISR が更新するオーバーフロー回数と現在のカウンタ値を
組み合わせて作られるので、オーバーフロー割り込みが保留のまま ISR 内で
`micros()` を呼ぶと**時刻が飛ぶ**。飛んだ幅が `capmark=7500` を超えれば
偽の「区切り」になる。ちょうどそれが 4 本立って転送が打ち切られた。

> **使える優先度は 9・10・11 の 3 つだけ。**
> USB (12) より高く、タイマ (8) より低くなければならない。

### 実験 C: 優先度 11 — 完全成功

```
R 1 bytes=50   data=48   hdr=10000/40/40  parity=001D calc=001D OK fe=0 noise=0
R 2 bytes=2808 data=2806 hdr=25848/20/20  parity=2304 calc=2304 OK fe=0 noise=0
DONE marks=4 bits=61694 blocks=2 glitch=0 ovf=0 dropped=0 ms=40048 status=ok
完全一致: True （sha256 26f3e7f18c1e...）
```

**取り込み中に `+D` 行を吐きながら、1 ビットも落とさずバイト単位で一致した。**

| 実験 | `capstream` | 優先度 | ビット数 | 結果 |
|:--|:--:|--:|--:|:--|
| 基準 | 0 | 12 | 61694 | 一致（2 回再現）|
| A | 1 | 12 | 61676 | **失敗**（18 ビット欠落）|
| B(1) | 1 | 12 のまま | 61677 | **無効**（優先度が適用されず）|
| B(2) | 1 | 4 | 2058 | **`micros()` 破綻**（偽の区切り 4 本）|
| **C** | **1** | **11** | **61694** | **完全一致** |

**原因は「USB と同一優先度で横取りできないこと」に確定。**

### 反映 (v0.4.0)

| 変更 | 内容 |
|:--|:--|
| `irqprio` の既定を **11** に | 書き込み直後・電源投入直後から効く |
| `capstream` を 3 値に | 0 = 自動（既定）、1 = 常に流す、2 = 常に貯める |
| 自動判定 | ブロックが 12 KB に収まるなら貯め、収まらないなら流す |
| `calib.cpp` にも同じ優先度を適用 | `CAL` も同じ理由でエッジを落としうる |
| `+R` に ` streamed` を追加 | どちらの方式で受けたかが結果に残る |

**自動判定ができる理由**: ブロック 2 の大きさは、ブロック 1 に入っている
`.bin` ヘッダのオフセット `0x12` の 16 ビット（リトルエンディアン）で分かる。
ブロック 1 が閉じてから PWM2 が始まるまでには 2 秒あるので、**始まる前に
方式を決められる**。

小さいデータでは「取り込み中に一切喋らない」という最も強い保証を保ったまま、
12 KB を超えるものだけ流す。実機の 27286 バイト全域が扱えるようになった。

### 既定を「常に流す」に変更（v0.5.0）

**大きさによらず取り込みながら流すことにした。**
将来ブラウザ（Web Serial）や GUI からこの環境を操作したときに、
**途中経過を表示したい**という要件があるため。

貯める方式は転送が終わるまで何も出ないので、40 秒間まったく状況が
分からない。流す方式なら `+D <blk> <off> <hex>` が届くたびに進捗を
描ける。安全性は実験 C で確かめてある。

あわせて **1 秒ごとの進捗を転送中も出す**ようにした。`+D` だけでは
PULSES1 の 8 秒と PWM1 のヘッダ 3.3 秒がまったくの無音になり、
生きているのかどうか分からないため。

```
CAP waiting 1s                                    ← BSAVE 待ち
CAP marks=1 bits=0     blk=0 bytes=0              ← 転送開始
CAP marks=1 bits=10532 blk=1 bytes=50             ← PWM1 完了
CAP marks=3 bits=23182 blk=2 bytes=0              ← PWM2 開始
CAP marks=3 bits=39585 blk=2 bytes=351
CAP marks=3 bits=50284 blk=2 bytes=1540
CAP marks=3 bits=61096 blk=2 bytes=2741
```

`bytes` はブロックごとの累計なので `blk` と対で読む。

**進捗率が正確に出せる。** ブロック 1 の 48 バイトが先に届き、その
オフセット `0x12` の 16 ビットが本体サイズなので、**PWM2 が始まる前に
総バイト数が確定する**。

`capstream=2` を選べば従来どおり転送中に完全に沈黙する。こちらは
割り込み優先度が正しいことに依存しない唯一の方式なので、
**優先度まわりを疑うときの逃げ道**として残してある。

**進捗バーには `bytes` ではなく `bits` を使うこと。**

```
CAP marks=3 bits=12536 blk=2 bytes=0      ← PWM2 のヘッダを消化中
CAP marks=3 bits=34021 blk=2 bytes=0      ← 8.4 秒間ずっと 0 のまま
CAP marks=3 bits=47718 blk=2 bytes=1255
```

PWM2 のヘッダは 25848 ビットあり、これを読み飛ばす **8.4 秒間は
1 バイトも復号されない**。`bytes` を見ていると止まって見える。
総ビット数は本体サイズから計算できる。

```
PWM1 = 10000 + 40 + 40 + 1 + (48 + 2) × 9 + 1 = 10532
PWM2 = 25848 + 20 + 20 + 1 + (N  + 2) × 9 + 1
```

### 失敗: 待機する前に BSAVE を実行してしまった

最終確認の 1 回目は、**取り込みが待機に入る前に実機が走り始めた**ため
失敗した。ファームウェアの問題ではない。

```
R 1 bytes=2808 data=2806 parity=2304 calc=2304 OK fe=0 noise=0 streamed
DONE marks=4 bits=51162 blocks=1 glitch=0 ovf=0 ms=90335 status=ok
ホスト: ブロックが揃っていない: [1]
```

原因は手順。「`BSAVE` を実行してください」と伝えてからコマンドを起動し、
しかも先頭に `sleep 3` を置いていたため、待機に入る前に転送が始まった。
**待機に入ったことを確認してから合図する**のが正しい。

失敗の中身は有益だった。

- `bits=51162` が **PWM2 だけの理論値と完全に一致**した。
  ビット数だけで「どこから拾い始めたか」が分かる
- PWM2 単独では 2806 バイト・パリティ OK・`fe=0` で完璧に復号された。
  **流す方式が正しく動いていることの追加の証拠**になった
- `blocks=1` とホストの「ブロックが揃っていない」で、
  **部分的なデータを正しいものとして保存せずに止まった**
- `ms=90335` が 40 秒の 2 倍以上あることも、2 回分の転送に
  またがったことを示していた

「最初の区切りを見るまでビットを捨てる」規則が、途中から拾った
信用できないデータを受け入れる事故を防いでいる。

### 検証（v0.5.0・既定設定・2854 バイト）

```
R 1 bytes=50   data=48   parity=001D calc=001D OK fe=0 noise=0 streamed
R 2 bytes=2808 data=2806 parity=2304 calc=2304 OK fe=0 noise=0 streamed
DONE marks=4 bits=61694 blocks=2 glitch=0 ovf=0 dropped=0 ms=40048 status=ok
```

**2 回連続でバイト単位一致**（`stream1.bin` / `stream3.bin`）。
どちらも総ビット数が理論値 61694 に一致。

### 将来の方向: Web Serial でエミュレータから実機へ直接

エミュレータ（ブラウザ上）から Web Serial でこのボードを叩き、
**実機と直接 `.bin` をやり取りする**構想がある。
今の設計はそのまま使える見込みで、理由は次のとおり。

| 設計 | Web Serial での意味 |
|:--|:--|
| 行指向・ASCII 16 進 | `TextDecoderStream` と行分割で扱える。バイナリのフレーミングが不要 |
| 先頭 1 文字が種別 (`+ ! # *`) | ストリームを読みながら分岐できる |
| 常に流す方式 | `+D` が届くたびに進捗を描ける |
| `+D` にオフセットが入る | 欠落に必ず気づく。再同期もできる |
| 終端が `+OK` か `!` の 2 つだけ | 読みながら終わりを判定できる |
| USB CDC なのでボーレート無関係 | `open({baudRate})` の値を気にしなくてよい |

**エミュレータは既に `.bin` を読み書きできるので、Web Serial 層は
`.bin` を運ぶだけでよい。** 信号形式の知識をブラウザ側に持ち込む必要は無い。

未確認の点。

1. **中断のバイト。** `ESC` (0x1B) / `Ctrl-C` (0x03) の 1 バイト送信で
   中断する規約を、ブラウザ側でも同じに合わせる必要がある
2. **`LOAD` のフロー制御。** `+RDY` のあと `D` 行を連続で送る作りだが、
   デバイス側の受信バッファが溢れないかは未実測。12 KB で 384 行になる
3. **ポートの排他。** ブラウザが掴んでいる間は `g850ctl.py` が使えない。
   切り分けのときに困る

### この段階で得られた知見

1. **`attachInterrupt` の優先度は既定のままでは足りない。**
   Arduino の `attachInterrupt` は USB と同じ優先度を設定する。
   マイクロ秒精度でエッジを測る用途では**必ず明示的に上げること**。
2. **上げすぎてもいけない。** タイマより高くすると `micros()` が壊れる。
   時刻を返す仕組みそのものが割り込みに依存していることを忘れない。
3. **「設定した値」ではなく「効いた値」を報告させる。**
   `#cap irqn=-1 prio=255` の 1 行が無ければ、実験 B の失敗を
   「優先度は無関係」と誤読していた。
4. **レジスタの差分で状態を探る方法は 1 回しか使えない。**
   2 回目以降は差分が出ない。見つけた結果を覚えておくこと。
5. **帯域と応答性は別の問題。** 必要な送出速度は毎秒 787 バイトで
   桁違いに足りていた。足りなかったのは割り込みの応答性だけ。
6. **待機に入ったことを確認してから相手に合図する。**
   確認せずに合図すると、転送の途中から拾って別の失敗になる。
7. **理論値はビット数で持っておくと切り分けに効く。**
   `bits=51162` が PWM2 単独の値と一致したことで、
   「どこから拾い始めたか」が 1 つの数字で分かった。

### この段階で得られた知見

1. **短縮タイミングは大きいデータでもそのまま通用する。** 22 バイトで確かめた
   `PROFILE FAST` が 2806 バイトでも 1 回で通った。ヘッダのビット数は
   データ量と無関係なので、大きいほど短縮の効果は薄れる
   （22 バイトでは 87%、2854 バイトでは 56% の時間削減）。
2. **取り込み中はシリアルに書いてはいけない。** これは設計上の見落としで、
   小さいデータでは絶対に表面化しない。
   **（段階 B で原因が判明し、割り込み優先度を上げれば書けるようになった。
   ただし「収まるなら貯める」という既定は安全側として残してある。）**
3. **`fe`（フレーミングエラー）は原因の切り分けに使える。**
   `fe > 0` なら受信側の問題、`fe = 0` でパリティだけ NG なら送信元の
   データが違う、と読み分けられる。
4. **`ovf = 0` は「取りこぼしていない」ことを意味しない。**
   リングバッファが溢れていなくても、割り込みが発火しなければ静かに落ちる。
5. **沈黙させる設計には、沈黙が始まったことを知らせる仕組みが要る。**
   進捗が止まったのが「始まった」のか「何も来ていない」のかを、
   受け手が区別できなければならない。
6. **理論値との突き合わせが効く。** 総ビット数・ヘッダのビット数を
   計算値と比べれば、パリティが合っていても分かるずれを見つけられる。
   61694 という数字が一致したことが、修正が効いた最も強い証拠になった。

## 段階 C: LOAD のフロー制御（2026-08-30・完了）

Web Serial から使う前に、**ホスト → デバイス方向で取りこぼしが起きないか**を
確かめた。実機は不要。

### 何が心配だったか

`LOAD` は `+RDY` のあと `D` 行を連続で送る作りで、**行ごとの応答を待たない**。
12288 バイトを 32 バイト行で送ると 384 行・27652 バイトになる。
デバイスが 1 行ずつ 16 進を解釈している間に次が届き続けるので、
受信バッファが溢れないかが未確認だった。

### 試験

pyserial は 1 行ごとに `write` + `flush` するため、OS がその都度掃けてしまう。
Web Serial から素朴に実装すると全部を 1 回で書くので、**27652 バイトを
1 回の `write` で投げる**形で試した。

| 条件 | 結果 |
|:--|:--|
| 1 行ずつ送る × 3（12288 / 4096 / 49 バイト）| **9 回すべて往復一致** |
| 1 回で全部書く（`+RDY` を待つ）× 3 | **CRC 一致 8B6D** |
| 1 回で全部書く（**`+RDY` を待たない**）× 3 | **CRC 一致 8B6D** |
| `DUMP` で戻して突き合わせ | **12288 バイト一致** |

**取りこぼしは起きなかった。** `LOAD` コマンドの直後に本体を続けて投げても
問題ない（USB CDC が NAK で背圧をかけるため）。

### 速度

| 経路 | 速度 |
|:--|:--|
| `LOAD` | ASCII **42 KB/s** / 実データ **19 KB/s**（12288 バイトで 638 ms）|
| `DUMP` | 12288 バイトで **416 ms** |

1 行のバイト数を 32 から 92 に増やしても 638 → 606 ms とほとんど変わらない。
**律速はデバイス側の行の解釈**であって USB ではない。

### 見つかった欠陥 1: 行が長すぎると原因が分からない

行バッファは 192 文字。`readLine` は溢れた分を**黙って切り詰めて**いた。
1 行 93 バイト（193 文字）で試すと、

```
+RDY 12288
!ERR offset 93 expected 92        ← 症状であって原因ではない
```

切り詰められた結果として次の行のオフセットがずれた、という形でしか
現れない。**「行が長すぎる」という本当の原因が報告されない。**

`readLine` が `READLINE_TOOLONG` (-2) を返すようにして、
`!ERR line too long at <位置> (max 92 bytes per line)` を出すようにした。

1 行の上限は **92 バイト**。192 文字から `"D XXXX "` の 7 文字を引いた
184 文字が 16 進 92 バイトにあたる。92 で成功、93 で失敗することを確認した。

### 見つかった欠陥 2: 失敗するとエラーが 131 行流れる

`LOAD` がエラーで `return` すると、**まだ届いていない数百行の `D ...` が
コマンドとして解釈される**。

```
+RDY 12288
!ERR offset 93 expected 92
!ERR unknown command D            ← これが 131 行
!ERR unknown command D
...
```

1 回の失敗でストリームが埋まり、次のコマンドを送る前に入力を捨てる必要が
あった。`END` を見るか 2 秒無音になるまで読み捨てる `loadDrain()` を入れ、
エラー経路をすべて経由させた。

### 修正後

| 条件 | 応答 | 直後の `PING` |
|:--|:--|:--|
| 正常（1 行 32 バイト）| `+RDY` `+BIN` `+OK` | 通る |
| 正常（1 行 92 バイト・上限）| `+RDY` `+BIN` `+OK` | 通る |
| 行が長すぎる（93 バイト）| `!ERR line too long at 0 (max 92 bytes per line)` | 通る |
| 行を 1 つ落とす | `!ERR offset 192 expected 160` | 通る |
| 宣言より多く送る | `!ERR too much data (declared 1000)` | 通る |

**エラーは必ず 1 行だけ**になり、直後のコマンドが**入力を捨てずに**通る。

`ABORT` とタイムアウトのときは読み捨てをしない。相手が止めているか
黙っているので、捨てるべきものが無いため。

### この段階で得られた知見

1. **背圧は効いていた。** USB CDC は受信バッファが埋まると NAK を返すので、
   ホスト側の `write` が待たされる。行ごとの応答を作る必要は無い。
2. **律速はデバイス側の解釈。** 1 行を長くしても速くならない。
   32 バイト行のままでよい。
3. **黙って切り詰めてはいけない。** 症状（オフセットのずれ）しか
   報告されず、原因（行が長すぎる）が見えなくなる。
4. **エラーで抜けるときは、途中まで来ている入力の後始末が要る。**
   行指向のプロトコルでは、残りが全部コマンドとして解釈される。
5. **プロトコルの文字列は ASCII に保つ。** ホストが `decode("ascii")` で
   読むので、日本語を混ぜると化ける。エラーメッセージも例外にしない。

## 段階 6: 送出中の USB 割り込みを止める（2026-08-30・完了）

送出の 12288 バイト制限を外すための地ならし。制限を外すには**再生しながら
ホストから食べる**しかなく、その前に「転送中にホストから流し込んでも波形が
乱れないか」を決着させる必要があった。

### 予想

送出は割り込みを使わずビジーウェイトで H の幅を作っているので、USB の ISR に
横取りされると H が伸びる。ビット 0 は 162usec、判定のしきい値は 284usec しか
ないので、**122usec 伸びれば化ける**。取り込み側は優先度で解決したが
（段階 A）、送出側は割り込みで動いていないので優先度では守れない。止めるしかない。

`usbmask=1`（既定）で、`usbmaskmax`（1000usec）以下の H を出す間だけ USB の
割り込みを `NVIC_DisableIRQ` で止める。区切りの 30msec のような長い H では
止めない。USB を長く待たせるうえ、そこでは幅の精度が要らない。

### 計器を 2 回作り直した

**1 回目の試験は成立していなかった。** ホストから雑音を流したつもりが、
17.6 秒のうち**最初の 0.4 秒しか届いていなかった**。送出中はファームウェアが
受信を一切読まないので、相手のバッファが詰まった時点で書き込みが止まる。

| 狙い | 実際に書けた |
|--:|--:|
| 352828 バイト | **8000 バイト** |

`playpump`（既定 1）を足し、L の区間ごとに受信を捌くようにして解決した。
これは制限を外すときに必要な処理そのものでもある。中断 (ESC) がビットの
合間で効くようになる副産物もついた。

**2 回目も計器が違っていた。** D3-D2 のループバックで読み返すと、
取り込み側の割り込み遅れと混ざって区別がつかない。雑音下ではパルスが
144〜319 本消えており、これは**取り込み側**が横取りされた症状である。
送出が乱れたのかどうかは、この測り方では分からない。

**出した側で測るようにした。** `driveXin(1)` の直後と `driveXin(0)` の直後で
`micros()` を取り、出したつもりのビットと、受信側が読むであろうビット
（H >= `capbit` なら 1）が食い違った本数を数える。`DONE` の行に
`hmax=` `hbad=` `hn=` として出す。

> **ループバックは送出と取り込みの両方を通る。片方だけを見たいなら、
> 見たい側で測る計器を作る。**

### 結果（`basen.bin` 2854 バイト / FAST / 33846 ビット）

| 条件 | 届いた雑音 | 出した H の最長 | **化けた本数** |
|:--|--:|--:|--:|
| `usbmask=1` 雑音なし | 0 | 418 usec | **0** |
| `usbmask=0` 雑音なし | 0 | 421 usec | **0** |
| **`usbmask=0` 雑音 20000B/s** | 328000 | **11197 usec** | **93** |
| **`usbmask=1` 雑音 20000B/s** | 327000 | 418 usec | **0** |

**マスク無しで負荷をかけると 162usec の H が 11.2 ミリ秒まで伸びる。**
93 本という数は 2 回の測定で一致した（`hover` で数えた 1 回目の
12016 - 11923 = 93 と、`hbad` で数え直した 2 回目の 93）。

静かな線では差が出ない（条件 1 と 2）。**雑音を流して初めて差が出る**ので、
負荷をかけずに「効いている」と判断してはいけない。

### 分かったこと

1. **USB の ISR は 11 ミリ秒 H を伸ばすことがある。** 予想していた
   「122usec の余裕を食う」どころではない。ストリーム化には必須。
2. **止めれば完全に防げる。** 最長 418usec は正規のビット 1（406usec）に
   ジッタが乗った程度で、化けは 0。
3. **雑音下では取り込み側が壊れる。** 送出中に毎秒 18KB も流すのは
   ストリーム化に必要な量（787 バイト/秒）の 23 倍で、実運用では起きない
   負荷だが、取り込みと送出を同時にやる設計にはできないことが分かる。

### 実機での確認（2026-08-30）

ジャンパを外し、ポケコンをつなぎ直して往復させた。**`NEW` を先に実行し、
`LIST` が空であることを確かめてから `BLOAD` で待たせている。**

```
# play n=2854 body=2806 bits=33846 usbmask=1 irqs=4
DONE n=2854 ms=17918 status=ok hmax=418 hbad=0 hn=33846
```

| 見たもの | 結果 |
|:--|:--|
| `usbmask` / `irqs` | 1 / 4（止めながら送出した）|
| `hbad` | **0**（33846 ビットのうち化けは無し）|
| `hmax` | 418 usec（正規のビット 1 は 406）|
| 実機の `BLOAD` | 正常終了 |
| `LIST` | `BASE-n` が復元された |
| `RUN` | 動いた |

**`usbmask` と `playpump` を入れても既存の経路は壊れていない。**
これで送出をストリーム化する土台ができた。

### 残り

クレジット式のフロー制御、ホスト側の対応）は未着手。
