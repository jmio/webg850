# USB Serial のコマンド仕様

Arduino Uno R4 Minima はネイティブ USB CDC なので、**ボーレートは実効的に
無関係**（名目 115200）。行末は LF。

## 応答の形式

**1 行 1 レコード**で、先頭 1 文字が種別を表す。

| 先頭 | 意味 |
|:--|:--|
| `+` | 正常応答・データ |
| `!` | エラー。**このコマンドはここで終わる** |
| `#` | 情報ログ・警告。処理は続く |
| `*` | 進捗 |

**すべてのコマンドは `+OK` で始まる行か `!` で始まる行で終わる。**
ホスト側はこの 2 つだけを終端として扱えばよい。

進捗の `*` 行は送信バッファに空きが無ければ**捨てられる**。
ホストが読まなくても波形のタイミングが崩れないようにするため。
`+` `!` `#` は捨てられない。

## なぜ 16 進か（バイナリの受け渡し）

`.bin` は生バイナリだが、**Arduino とのやり取りには ASCII の 16 進を使う。**
USB CDC は 8 ビット透過なので生バイナリも技術的には通せるが、次の理由で採らない。

1. **コマンドが行指向である。** 生バイナリを混ぜるには長さ指定でモードを
   切り替える必要があり、一度ずれると復帰が難しい。16 進なら行の単位が
   保たれるので、どこで壊れたかが分かり、再同期もできる。
2. **中断用のバイトとぶつかる。** 長時間動作は `ESC` (0x1B) と
   `Ctrl-C` (0x03) で中断する設計にしてある。生バイナリにはこの値が普通に
   現れる。
3. **素の端末で見える。** シリアルモニタを開いたまま手で叩いて調べられる。
   解析用の道具としてはこれが効く。
4. **速度が問題にならない。** 最大 12 KB なので 16 進でも 24 KB。
   USB CDC では一瞬で、`PLAY` の 26 秒に比べれば無視できる。

Base64 なら 1.33 倍で済むが、可読性を失う割に得られる時間が無い。
Intel HEX も候補だが、`.bin` は**メモリイメージではなく信号のイメージ**なので
アドレス欄に意味が無く、形式を偽ることになる。
（`BSAVE M` が別に吐く `.ihx` は本物のメモリイメージなので Intel HEX が正しい。
ここで扱う `.bin` とは別物。）

行の形は次のとおり。オフセットを載せてあるので、途中の行が落ちれば必ず気づく。

```
D <offset:16進4桁> <データ:16進>
```

1 行あたり 32 バイト。ホスト → デバイス（`LOAD`）でもデバイス → ホスト
（`DUMP` / `CAP`）でも同じ形。`CAP` だけはブロック番号が入る（後述）。

## コマンド一覧

### 疎通・情報

| コマンド | 応答 |
|:--|:--|
| `PING` | `+PONG <name> <ver>` / `+OK` |
| `INFO` | `+INFO ...` × 3 / `+OK` |
| `PINS` | `+PINS xout=<0/1> busy=<0/1> ack=<0/1> xin=<L/H/Z>` / `+OK` |
| `IRQ` | 使用中の割り込みスロットを `+IRQ <番号> event=<16進> prio=<優先度>` で列挙 |

### タイミング

| コマンド | 内容 |
|:--|:--|
| `CFG` | 全部の設定値を `+CFG <key>=<value>` で列挙 |
| `CFG <key> <value>` | 1 つ設定する。`value` は 10 進か `0x` 付きの 16 進 |
| `PROFILE REAL` | 実機と同じ波形（22 バイトで 26.5 秒）|
| `PROFILE FAST` | 短縮タイミング（22 バイトで 3.33 秒）。**起動時の既定** |

タイミングの既定値は **2026-08-30 に実機で測った値**（推定値ではない）。
書き込み直後・電源投入直後からそのまま使える。
起動時のプロファイルは `src/config.h` の `DEFAULT_PROFILE_FAST` で選ぶ。

| `hdr2` | 25848 | PWM2 ヘッダの 0 の個数 |

### データ転送

```
LOAD <n>
  ← +RDY <n>
  → D 0000 0220202020...
  → D 0020 ...
  → END
  ← +BIN n=.. body=.. declared=.. mode=.. addr=.. crc=.. sizeok
  ← +OK n=<n> crc=<hhhh>
```

`n` は 49 以上 12288 以下。オフセットが飛んだり 16 進が壊れていたら `!ERR`。

**1 行は 92 バイトまで。** デバイスの行バッファが 192 文字で、
`"D XXXX "` の 7 文字を除いた 184 文字が 16 進 92 バイトにあたる。
超えると `!ERR line too long`。ホスト側の既定は 32 バイト。

**フロー制御は要らない。** 行ごとの応答を待つ必要はなく、
`LOAD n` の直後に本体を続けて 1 回で書いてよい（`+RDY` を待たなくても
通る）。USB CDC が NAK で背圧をかけるため取りこぼさない。
12288 バイト（27652 文字・384 行）を 1 回の書き込みで投げて確認済み。

| 経路 | 速度 |
|:--|:--|
| `LOAD` | ASCII 42 KB/s / 実データ 19 KB/s（12288 バイトで 638 ms）|
| `DUMP` | 12288 バイトで 416 ms |

1 行を 92 バイトにしても 638 → 606 ms でほとんど変わらない。
**律速はデバイス側の行の解釈**なので、行を長くする意味は薄い。

**失敗したときはエラーが 1 行だけ返る。** デバイスは `END` を見るか
2 秒無音になるまで残りの行を読み捨てるので、次のコマンドをそのまま
送れる（入力を捨て直す必要は無い）。ただし `ABORT` とタイムアウトの
ときは読み捨てをしない。

| エラー | 意味 |
|:--|:--|
| `!ERR size <n> (49..12288)` | `LOAD` の `n` が範囲外。`PLAYS` に上限は無い |
| `!ERR line too long at <位置> (max 92 bytes per line)` | 1 行が長すぎる |
| `!ERR offset <実際> expected <期待>` | 行が飛んだか順序が違う |
| `!ERR bad hex at <位置>` | 16 進が壊れている |
| `!ERR too much data (declared <n>)` | 宣言より多い |
| `!ERR short <got> of <n>` | `END` が来たが足りない |
| `!ERR timeout at <位置>` | 10 秒来なかった |
| `!ERR aborted` | `ABORT` を受けた |

**行と行の間が 10 秒空くとタイムアウトする。** 送信を長く止めないこと。

| コマンド | 内容 |
|:--|:--|
| `DUMP` | バッファの内容を `+D 0 <off> <hex>` で吐く。末尾に `+OK n=.. crc=..` |
| `BIN` | バッファのヘッダ情報だけ表示する |

### 実験 A: 再生

```
PLAY [delay_ms]
  ← #play n=.. body=.. bits=.. usbmask=<0|1> irqs=<本数>
  ← *PLAY <済み>/<総数> <%>       ← 300ms ごと
  ← +DONE n=.. ms=.. status=ok|aborted hmax=.. hbad=.. hn=..
  ← +OK
```

`DONE` の `hmax` / `hbad` / `hn` は**出した側で測った H** の記録。

| | 内容 |
|:--|:--|
| `hmax` | 短い H の最長 [usec]。正常なら 418 前後（ビット 1 の 406 + ジッタ）|
| `hbad` | **化けた本数。** 出したつもりのビットと、受信側が読むであろうビット（H >= `capbit` なら 1）が食い違った数 |
| `hn` | 測った本数 |

**`hbad` が 0 でなければ、受信側は違うビットを読んでいる。**
ループバックで読み返した値と混同しないこと。あちらは取り込み側の
割り込み遅れも乗るので、送出だけを見たいときはこの `hbad` を使う。

`delay_ms` は送出を始めるまでの待ち。実機で `BLOAD` を実行してから
`PLAY` を打つのが基本なので、通常は 0 でよい。

送出中は `ESC` (0x1B) か `Ctrl-C` (0x03) を 1 バイト送れば中断する。

#### 貯めずに流す `PLAYS`（大きさの上限なし）

```
PLAYS <n> [delay_ms]
  ← #plays n=.. body=.. bits=.. usbmask=.. irqs=..
  ← +RDY <n>                     ← これを見てから流し始める
  → <16 進の文字列>              ← 行の接頭辞は要らない。改行・空白は自由
  ← *PLAY <済み>/<総数> <%>
  ← +DONE n=.. ms=.. status=ok|aborted|underrun hmax=.. hbad=.. hn=..
           fed=.. under=..
  ← +OK
```

`LOAD` + `PLAY` は .bin を丸ごと RAM に貯めるので **12288 バイトが上限**で、
RAM の都合で 13824 までしか増やせない。実機の空き容量 27286 バイトに届かない。
`PLAYS` は 512 バイトのリングしか使わないので**上限が無い**。

**フロー制御は無い。要らない。** リングが埋まればデバイスは読むのをやめ、
USB が NAK を返してホストの書き込みが止まる。詰まりをそのまま流量調整に
使っている。ホストは黙って全部書けばよい。

| 返り値 | 内容 |
|:--|:--|
| `fed` | 受け取ったバイト数。`n` と一致すること |
| `under` | データ待ちで止まった回数。**0 でなくても壊れない**（待つのはビットの合間、つまり L の区間なので H の幅に影響しない）|
| `status=underrun` | 10 秒待っても続きが来ず、あきらめた |

`LOAD` にあった CRC の突き合わせは無い。代わりに `fed` と `hbad` で見る。

#### 送出中の USB 割り込み `usbmask`

**送出は割り込みを使っていない。** ビジーウェイトで H の幅を作っているので、
割り込みはどれでもこれを横取りする。USB の ISR が H の最中に走ると H が
その分だけ伸びる。

| | 値 |
|:--|--:|
| ビット 0 の H | 162 usec |
| ビット 1 の H | 406 usec |
| 判定のしきい値 (`capbit`) | 284 usec |
| **ビット 0 が化けるまでの余裕** | **122 usec** |

取り込み側は同じ問題を優先度で解いた（`irqprio`）。送出側は割り込みで
動いていないので優先度では直せない。**止めるしかない。**

`usbmask=1`（既定）なら、`usbmaskmax` 以下の H を出す間だけ USB の
割り込みを止める。区切りの 30msec のような長い H では止めない。USB を
長く待たせるうえ、そこでは幅の精度が要らないため。

`#play` の行に `irqs=` として**実際に見つかった USB のスロット数**を出す。
`irqs=0` なら止められていない。`IRQ` コマンドの一覧でも USB のスロットには
` usb` が付く。設定値ではなく効いた値を見ること（`irqprio` で一度、
適用されていないことに気付かず誤った結論を出しかけた）。

ホストから雑音を流して負荷をかけられる。

```
python host/g850ctl.py -p COM16 selftest --fast --stress 2000 <bin>
```

送るのは改行だけで、ファームウェアは空行を黙って捨てる。転送中は
`pumpInput()` が `ESC` と `Ctrl-C` 以外を読み捨てるので、届いても
波形には関係しない。**起こしたいのは USB の割り込みだけ。**

実機で測った結果（`basen.bin` 2854 バイト / FAST / 33846 ビット）。

| 条件 | 届いた雑音 | `hmax` | `hbad` |
|:--|--:|--:|--:|
| `usbmask=1` 雑音なし | 0 | 418 usec | 0 |
| `usbmask=0` 雑音なし | 0 | 421 usec | 0 |
| **`usbmask=0` 雑音 20000B/s** | 328000 | **11197 usec** | **93** |
| **`usbmask=1` 雑音 20000B/s** | 327000 | 418 usec | 0 |

**USB の ISR は H を 11 ミリ秒伸ばすことがある。** 静かな線では差が出ない
ので、負荷をかけずに「効いている」と判断してはいけない。経緯は
[experiment-log.md](experiment-log.md) の段階 6。

| コマンド | 内容 |
|:--|:--|
| `IDLE 0\|1\|Z` | XIN の待機時の駆動。`Z` は入力に戻す（起動直後は `Z`）|
| `ACK 0\|1\|Z` | 11pin の 9 番を駆動する。TEXT SIO の flow 調査用 |

### 実験 B: 取り込み

```
CAP [sec]
  ← #cap armed timeout=..ms mode=irq stream=0
  ← #cap irqn=5 prio=11                ← 実際に適用された割り込み優先度
  ← *CAP waiting 1s                    ← 転送が始まるまで 1 秒ごと
  ← #cap begin mark=30021us            ← 転送を検出
  ← +D 1 0000 0220202020...            ← 32 バイトごとに届く
  ← *CAP marks=1 bits=10532 blk=1 bytes=50    ← 1 秒ごと
  ← +D 2 0000 ff000300...
  ← *CAP marks=3 bits=39585 blk=2 bytes=351
  （…転送が終わるまで繰り返し…）
  ← *MARK 1 30021us                    ← 区切りは転送終了後にまとめて出る
  ← *MARK 2 30022us
  ← *MARK 3 30026us
  ← *MARK 4 30023us
  ← #block 1 begin
  ← +R 1 bytes=50 data=48 hdr=10000/40/40 parity=001D calc=001D OK fe=0 noise=0 streamed
  ← #block 2 begin
  ← +R 2 bytes=2808 data=2806 hdr=25848/20/20 parity=2304 calc=2304 OK fe=0 noise=0 streamed
  ← +DONE marks=4 bits=61694 blocks=2 glitch=0 ovf=0 dropped=0 ms=40048 status=ok
  ← +OK
```

- `+D <ブロック番号> <オフセット> <16進>` — 復号したバイト列。
  **パリティ 2 バイトを含む。** ホスト側で末尾 2 バイトを落とすこと。
- `+R <ブロック番号> ...` — ブロックの要約。`data=` がパリティを除いた長さ。
  取り込みながら流したブロックには末尾に ` streamed`、
  貯めきれなかったブロックには ` TRUNCATED` が付く。
- ブロック 1 が `.bin` のヘッダ 48 バイト、ブロック 2 が本体になる。
- `*CAP marks=.. bits=.. blk=.. bytes=..` — 1 秒ごとの進捗。
  `bytes` はブロックごとの累計なので `blk` と対で読むこと。
- **区切りの長い H を 4 回見た時点で 1 回の転送が終わったとみなす。**
- 途中から拾ったビットは信用できないので、**最初の区切りを見るまで
  ビットを捨てる。**
- `ovf` はリングバッファの取りこぼし。0 でないと結果は信用できない。
  **ただし `ovf=0` は「取りこぼしていない」ことを意味しない**（下記）。
- `dropped` は 12 KB を超えて捨てたバイト数。

#### 取り込み中の出力

**復号したバイトの吐き出し方は 2 通りあり、`capstream` で選ぶ。**

| `capstream` | 動作 | いつ使うか |
|:--:|:--|:--|
| **1** | 32 バイトごとに取り込みながら `+D` を吐く | **既定。** 途中経過を見せたいとき |
| 0 | 12 KB に収まるなら貯め、収まらないなら流す | 小さいデータで最も安全にしたいとき |
| 2 | 常に貯め、転送が終わってから吐く | 転送中に完全に沈黙させたいとき |

既定を「常に流す」にしてあるのは、**ホスト側に進捗を表示できるようにする
ため**。`+D <blk> <off> <hex>` が届くたびに描ける。

**進捗率が正確に出せる。** ブロック 1 の 48 バイトが先に届き、その
オフセット `0x12` の 16 ビット（リトルエンディアン）が本体サイズなので、
**PWM2 が始まる前に総バイト数が確定する。**

流したブロックは `+R` の末尾に ` streamed` が付く。
`capstream=2` で貯めきれなかった場合は ` TRUNCATED`。

`capstream=2` だけは転送中に一切書かないので、**割り込み優先度が
正しいことに依存しない唯一の方式**。優先度まわりを疑うときの逃げ道。

**流す方式が成立するのは `irqprio` が正しく設定されているときだけ。**
既定の優先度 12 のまま流すと、大きいデータでビットが落ちる。

#### 割り込み優先度 `irqprio`（**9〜11 以外にしないこと**）

実機で確かめた制約。

| 割り込み | 優先度 | 意味 |
|:--|--:|:--|
| millis / micros のタイマ | **8** | これより高くすると `micros()` が飛ぶ |
| **エッジ割り込み** | **11**（既定）| ここに置く |
| USB FS（4 本）| **12** | これと同じだと横取りできない |

- **12 のまま**（`attachInterrupt` の既定）→ USB の ISR が動いている間に
  エッジが 2 回来ると 1 ビット消える。2854 バイトの転送で 18 ビット欠落した
- **8 以下**（例: 4）→ タイマを横取りして `micros()` が飛び、
  偽の区切りが立って転送が途中で終わる

`CAP` は冒頭で `#cap irqn=<番号> prio=<値>` を出す。
**これは設定値ではなく実際に適用された値**なので、疑わしいときはここを見る。
`irqn=-1` は割り込み番号を突き止められなかったことを意味し、
そのときは優先度が設定されていない。

経緯は [experiment-log.md](experiment-log.md) の「段階 B」。

### 較正

```
CAL [sec]
  ← #cal armed timeout=..ms mode=irq
  ← *CAL waiting <秒> edges=..          ← 転送が始まるまで 1 秒ごと
  ← +H <level> <usec> <個数>            ← ヒストグラム（1usec 刻み、0 以外だけ）
  ← +L <番号> <level> <usec>            ← 1024usec を超えた区間
  ← +DONE edges=.. long=.. longover=.. span_us=..
  ← +OK
```

`level` は 1 が H、0 が L。

エッジを 1 本ずつ保存する `RAW` と違い、**転送の全区間**を対象にできる。
7 万本を超えるエッジは RAM に入らないが、ヒストグラムなら 4KB で足りる。
統計は割り込みハンドラの中で直接積んでいる。

ホスト側の `g850ctl.py cal` がこの出力からかたまりを見つけて
`bit0` / `bit1` / `mark` / `p1l` … を決め、`--apply` で書き戻す。

`CAP` と同じ理由で、**進捗は最初の区切りを見るまでしか出さない。**
区切りを 4 本数えた時点で打ち切るので、指定した秒数を待ち切ることはない。

### 生のエッジ列

```
RAW [sec] [max_edges]
  ← +E <番号> <level> <usec>
  ← +DONE edges=.. ovf=.. status=ok
  ← +OK
```

最大 3072 本。転送の**構造**（PULSES の順序）を目で確かめるのに使う。
**幅の統計を取るなら `CAL` を使うこと。**
ヘッダの 0 が 1 万個続く区間で `RAW` は埋まってしまう。

### 自己検証（実機不要）

| コマンド | 必要なもの | 確かめられること |
|:--|:--|:--|
| `DECTEST` | 何も要らない | ビット列の組み立てと復号が往復で一致するか |
| `SELFTEST [delay_ms]` | D3→D2 のジャンパ | 自分が出したパルス幅が意図どおりか |

```
DECTEST
  ← +T PWM1 len=48 got=48 bad=0 hdr=10000/40/40 parity=0018 calc=0018 fe=0 OK
  ← +T PWM2 len=22 got=22 bad=0 hdr=25848/20/20 parity=002D calc=002D fe=0 OK
  ← +OK PASS
```

`SELFTEST` は `PLAY` と同じ波形を出しながら D2 で読み返し、
`CAL` と同じヒストグラムを返す。**実機はつないだままにしないこと**
（出力同士がぶつかる）。

## 中断

長時間動作するコマンド（`PLAY` / `CAP` / `RAW` / `CAL` / `SELFTEST`）の実行中は、
`ESC` (0x1B) か `Ctrl-C` (0x03) を 1 バイト送れば中断する。
それ以外の受信バイトは捨てられる（コマンドは受け付けない）。

`LOAD` の途中は例外で、`ABORT` という行を送ると中断する。
