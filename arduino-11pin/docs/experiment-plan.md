# 実験計画: Arduino Uno R4 Minima ↔ PC-G850 実機 11pin I/O

作成日: 2026-08-30

エミュレータ上で確定させた `BSAVE` / `BLOAD` の PWM 信号形式が、**実機に対しても
そのまま通用するか**を確かめる実験の計画書。

- 実験は Arduino Uno R4 Minima（ファームウェアは PlatformIO で開発）と
  ホスト PC（USB Serial 経由でコマンドを送る）で行う。
- 本フォルダ [../](../) 以下がこの実験専用の作業領域で、得られた知見は
  すべて本 `docs/` に置く。

---

## 1. 目的

大きく 2 つ。

| # | 実験 | 内容 |
|:--|:--|:--|
| **A** | **再生（書き込み）** | エミュレータが吐いた `bsave.bin` から PWM 波形を組み立て、Arduino から 11pin の XIN へ流し込んで、実機の `BLOAD` / `BLOAD M` で読み込ませる |
| **B** | **取り込み（読み出し）** | 実機で `BSAVE` / `BSAVE M` を実行し、11pin の XOUT に出る波形を Arduino でキャプチャ・復号して `bsave.bin` を復元する |

最終的に確かめたいのは次の 3 点。

1. **往復の同一性** — 実機で `BSAVE` → Arduino で取り込み → Arduino から再生 →
   実機で `BLOAD` して、元と同じプログラム／メモリ内容が戻ること。
2. **エミュレータとの互換性** — エミュレータで作った `.bin` が実機で読め、
   実機で作った `.bin` がエミュレータで読めること。**実機とエミュレータの間で
   ファイルを行き来させられる**ようになるのが実用上のゴール。
3. **タイミングの実測値** — エミュレータで得た「実機相当」の推定値
   （9/8 倍換算）が実機と合っているかの検証と、短縮波形の許容下限。

> **2026-08-30 到達点: 1〜3 の主要部分は達成済み。**
>
> | # | 結果 |
> |:--|:--|
> | 1 | **達成。** Arduino → 実機 → Arduino の往復で 70 バイト完全一致 |
> | 2 | **達成。** 実機から取り込んだ `.bin` がエミュレータ由来の `bsave-test.bin` と完全一致 |
> | 3 | **達成（下限を除く）。** `bit0`=162 / `bit1`=406 が実測で一致し、実機は 8.00 MHz と確定。短縮波形の下限（段階 4）は未実施 |
>
> 副産物として **XIN の極性が反転している**ことが判明した（2.3 節）。
> 詳細は [experiment-log.md](experiment-log.md)。

### 2.1 11pin のピン配置

出典: *SHARP PC-G850V(S) User Manual / Interface, Appendix A: 11-Pin Interface*
（<https://wrabetz.com/resources/Sharp_PC-G850VS_Interface.pdf>, Version 1.1, 2016）

本体を**左側から見て、pin-1 が左端、pin-11 が右端**。

| Pin | SIO モード | SSIO/PWM モード | PIO モード | PIC モード |
|:--|:--|:--|:--|:--|
| 1 | -- | -- | -- | -- |
| 2 | VCC(+5V) | VCC(+5V) | VCC(+5V) | VCC(+5V) |
| 3 | GND | GND | GND | GND |
| 4 | RTS (O) | **BUSY (O)** | Bit0 (I/O) | CP (O) |
| 5 | DTR (O) | DOUT (O) | Bit1 (I/O) | CLK# (O) |
| 6 | RXD (I) | **XIN (I)** | Bit2 (I/O) | DATAIN (I) |
| 7 | TXD (O) | **XOUT (O)** | Bit3 (I/O) | DATAOUT (O) |
| 8 | CD (I) | DIN (I) | Bit4 (I/O) | LOWBATT# (I) |
| 9 | CTS (I) | ACK (I) | Bit5 (I/O) | -- |
| 10 | DSR (I) | EX1 (I) | Bit6 (I/O) | -- |
| 11 | CI (I) | EX2 (I) | Bit7 (I/O) | -- |

I/O の向きは**実機から見た向き**。`BSAVE` / `BLOAD` は SSIO/PWM モードで動き、
**使うのは pin-7 (XOUT) と pin-6 (XIN)、それに pin-3 (GND) の 3 本だけ**である。

### 2.2 信号レベル

同資料より。

| | 論理 | 電圧 | データ信号 (RXD,TXD) の意味 |
|:--|:--|:--|:--|
| RS-232 | LOW | -15V〜-3V | 1 (Mark), Idle, Stop |
| | HIGH | +3V〜+15V | 0 (Space), Start |
| UART-TTL | LOW | 0V | 0 (Space), Start |
| | HIGH | +3.3V/+5V | 1 (Mark), Idle, Stop |
| **PC-G850V(S)** | **LOW** | **0V** | **1 (Mark), Idle, Stop** |
| | **HIGH** | **5V** | **0 (Space), Start** |

つまり実機は **5V TTL で、論理は RS-232 と同じ向き（反転 UART-TTL）**。
Arduino Uno R4 Minima も 5V ロジックなので、**レベル変換なしで直結できる**。

### 2.3 I/O ポートのビットと物理レベルの対応

エミュレータの実測と上表を突き合わせると、**ポートのビット値がそのまま
物理レベル**であると読める。

- [io-ports.md](../../docs/analysis/io-ports.md): `18H` は「0=L 出力、1=H 出力」
- [text-sio.md](../../docs/analysis/text-sio.md): SIO のアイドル（論理 1）のとき `0x18` bit7 = 0
- 上の PDF の表: 論理 1 (Idle) = LOW = 0V

3 つが矛盾なく一致する。したがって:

| ポート | ビット | 11pin | 物理レベル |
|:--|:--|:--|:--|
| `0x18` (out) | bit7 | pin-7 XOUT | 1 → 5V (H) / 0 → 0V (L) |
| `0x1F` (in) | bit2 | pin-6 XIN | 5V (H) → 1 / 0V (L) → 0 |

> **2026-08-30 実測で決着: XIN 側は反転していた。**
>
> | ポート | ビット | 11pin | 物理レベル | 向き |
> |:--|:--|:--|:--|:--|
> | `0x18` (out) | bit7 | pin-7 XOUT | 1 → 5V | 非反転 |
> | `0x1F` (in) | bit2 | pin-6 XIN | **1 ⟺ 0V** | **反転** |
>
> 上の表の XIN の行は**誤り**だった。ファームウェアの既定は `invout=1`。
> 経緯と理由は [waveform.md](waveform.md) の「極性」を参照。

### 2.4 送出する波形（実機相当の「初期値」）

エミュレータの実測値を 9/8 倍して実機換算したもの。外部資料の実機実測とも一致する。

**ただしこれは推定値であって、そのまま信じて送出を始めてはいけない。**
理由は 5 節の冒頭にまとめた。実際に使う値は段階 1 の較正で置き換える。

```
PULSES1 : H(30ms) → L(8000ms)
PWM1    : 0×10000 → 1×40 → 0×40 → START(1) → [1+8bit]×48 → [1+8bit]×2(パリティ) → STOP(1)
PULSES2 : L(2000ms) → H(30ms) → L(24ms) → H(30ms) → L(6ms)
PWM2    : 0×25848 → 1×20 → 0×20 → START(1) → [1+8bit]×N → [1+8bit]×2(パリティ) → STOP(1)
PULSES3 : L(4000ms) → H(30ms)
```

| 要素 | 実機相当 |
|:--|--:|
| ビット 0 | H 162 usec → L 162 usec |
| ビット 1 | H 406 usec → L 406 usec |
| 区切り（長い H）| 30 ms |

- **ビットの値は H の長さだけで決まる。L の長さは受信側が見ていない**
  （[bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md) の実測）。
  これは送出中にホストへ進捗を出すなど、L 期間に他の処理を挟んでよいことを意味する。
- データは **MSB ファースト**。各バイトの前に必ず 1 のスタートビットが付く。
- パリティは**データ部の 8 ビット群に含まれる 1 の総数**を 16 ビット・
  ビッグエンディアンにしたもの。パリティ自身は数に入れない。
- 区切りの長い H は 1 回の転送でちょうど **4 回**。4 回目で転送終了と判断できる。

`.bin` は「48 バイトのヘッダ（= PWM1 のデータ部）+ 本体（= PWM2 のデータ部）」の
生バイナリで、パリティは保存しない（送出時に計算し直す）。

## 3. ハードウェア構成

### 3.1 配線

| 11pin | 信号 | 向き（実機視点）| Arduino Uno R4 Minima | Arduino の向き |
|:--|:--|:--|:--|:--|
| 3 | GND | -- | GND | -- |
| 7 | XOUT | 出力 | **D2** | 入力（外部割り込み） |
| 6 | XIN | 入力 | **D3** | 出力（1kΩ 直列） |
| 4 | BUSY | 出力 | D4 | 入力（監視のみ・任意） |
| 9 | ACK | 入力 | D5 | 既定は Hi-Z（任意） |

- **pin-2 (VCC) は接続しない。** 実機側の 5V を Arduino に引き込む必要はなく、
  互いに電源を持つ機器同士を VCC で結ぶのは事故のもと。GND だけ共通にする。
- **D2 を XOUT に割り当てるのは外部割り込みを使うため。** キャプチャは
  ピン変化割り込みでエッジ時刻をリングバッファに積み、復号は主ループで行う。
  こうしておけば USB シリアルの送信が詰まってもエッジを取りこぼさない。
- **XIN 側には 1kΩ を直列に入れる。** 万一こちらが出力しているときに実機側も
  出力していた場合の保護。信号は 3kHz 程度なので 1kΩ でも波形は鈍らない。
- BUSY / ACK は `BSAVE` / `BLOAD` では使われていないはずだが、
  「本当に使っていないか」を確かめるために監視だけできるようにしておく。

11pin コネクタは 2.54mm ピッチなので、汎用のピンヘッダで刺さる
（同資料の「USB PC-Adaptor Cable」の項でもそう案内されている）。

### 3.2 通電前の安全確認（必須）

**配線したらいきなり通信を始めず、次を順に確かめる。**

1. 実機の電源を入れ、Arduino を**つながない**状態でテスターを当て、
   pin-3 (GND) 基準で pin-7 (XOUT) のアイドル電圧を測る。**0V に近いこと**
   （2.2 節より、アイドル = 論理 1 = LOW = 0V のはず）。
2. `BSAVE` を実行して pin-7 が 5V まで振れることを確認する。
   **3.3V 程度しか出ないなら本体は 3.3V 系**なので、この計画の直結前提を見直す。
3. Arduino の D3 を**入力のまま**で GND と pin-3 だけ結線し、
   D2 に pin-7 を入れて `RAW` コマンドで波形が見えることを確認する。
   ここまでは Arduino から一切出力しないので実機を壊す余地がない。
4. その後はじめて D3 を出力にして XIN を駆動する。

## 4. ファームウェアとホストツールの構成

### 4.1 方針

- **PlatformIO**（`platform = renesas-ra` / `board = uno_r4_minima`）でビルドする。
- Arduino とホストは **USB Serial の行指向コマンド**でやり取りする。
  Uno R4 Minima はネイティブ USB CDC なのでボーレートは実効的に無関係
  （名目 115200）。
- バイナリはすべて **16 進テキスト**で運ぶ。デバッグしやすさを優先する。
  速度は問題にならない（最大でも数十 KB）。
- 応答は 1 行 1 レコードで、先頭 1 文字が種別。

  | 先頭 | 意味 |
  |:--|:--|
  | `+` | 正常応答・データ |
  | `!` | エラー |
  | `#` | 情報ログ |
  | `*` | 進捗 |

### 4.2 主なコマンド（詳細は別途 protocol.md に起こす）

| コマンド | 用途 |
|:--|:--|
| `PING` / `INFO` | 疎通確認・構成表示 |
| `CFG [key val]` | タイミング定数などの表示・変更 |
| `PROFILE REAL\|FAST` | 実機相当タイミング／短縮タイミングの一括切替 |
| `LOAD <n>` → `D <hex>` … `END` | `.bin` を Arduino のバッファへ転送 |
| `DUMP` | バッファの内容を取り出す |
| `PLAY [delay_ms]` | バッファの内容を PWM 波形として XIN へ送出（実験 A）|
| `CAP [sec]` | XOUT を取り込み、PWM を復号してバイト列を返す（実験 B）|
| `RAW [sec] [max]` | 生のエッジ列（レベルと継続時間）を返す。波形調査用 |
| `PINS` / `IDLE` / `ACK` | ピンの読み書き |

長時間動作するコマンド（`PLAY` / `CAP` / `RAW`）は、ホストから `ESC` (0x1B) または
`Ctrl-C` (0x03) を 1 バイト送れば中断できるようにする。

### 4.3 ホストツール

`host/g850ctl.py`（pyserial）でコマンドを叩き、`.bin` の読み書き・復号結果の
組み立て・パリティ検証を行う。

加えて `host/pwmcodec.py` に **Python の参照実装**（`.bin` → ビット列 → `.bin`）を
置く。実機に触る前にホスト側だけで往復テストができ、
ファームウェアの復号器と突き合わせる基準になる。

## 5. 実験の手順

段階を分け、**前の段階が通ってから次へ進む。** 途中で想定と違う結果が出たら
そこで記録して原因を切り分ける。

### 進める順序についての方針: 「測ってから出す」

**一番の懸念は時間軸方向のスケールである。**

再生（実験 A）から始めると、うまくいかなかったときに原因が

- パルス幅が実機の判定しきい値から外れている
- ビット列の組み立てが違う
- 極性が逆
- そもそも配線が違う

のどれなのか切り分けられない。しかも**送出側のタイミングを何を基準に
直せばよいかの手がかりが無い。** 推定値（9/8 換算）を上下に振って総当たりする
ことになり、1 回の試行に 26 秒かかるので現実的でない。

タイミングがずれうる根拠は具体的にある。

- 9/8 という比はエミュレータのクロック設定（9000 kHz）と実機の推定値
  （8 MHz）の比から出しただけで、実機で測ったものではない
- 実機の CPU クロックはポート `67H` で 8MHz / 4MHz が切り替わる。
  `BSAVE` / `BLOAD` の実行中にどちらであるかは確認していない
- `BSAVE` はソフトウェアのビットバンギングなので、**パルス幅は
  CPU クロックに直結する**

そこで、**実機が実際に出している波形を先に測り、その実測値で送出側の
定数を決める**。同じ ROM のルーチンが送受で対になっている以上、
**実機が出す幅をそのまま返せば必ず受かる**はずで、これが一番確実な較正になる。

順序は次のとおり。

```
段階 0  配線とレベルの確認          … 実機に触らずに済む範囲
段階 1  CAL: 実機の BSAVE を測る    ← 時間軸の基準をここで決める
段階 2  CAP: 取り込んで .bin を復元 … 実験 B
段階 3  PLAY: 再生して BLOAD させる … 実験 A（段階 1 の実測値を使う）
段階 4  短縮波形の下限を測る
段階 5  （任意）TEXT モードの SIO
```

**実験 B（取り込み）が実験 A（再生）の前提になっている。**
これは「実験 A を後回しにする」という意味ではなく、
**実験 A を一発で通すために実験 B を先にやる**という意味である。

なお、実機なしで先に潰せる不確かさは firmware 側で潰してある。

| コマンド | 実機 | 配線 | 確かめられること |
|:--|:--|:--|:--|
| `DECTEST` | 不要 | 不要 | ビット列の組み立てと復号が往復で一致するか |
| `SELFTEST` | 不要 | D3→D2 のジャンパのみ | 自分が出したパルス幅が意図どおりか |

`host/pwmcodec.py selftest` はさらに、ホスト側の独立実装で同じ往復を確かめる。
**この 3 つが通っていれば、実機で残る問題は「タイミング」と「レベル」だけに絞れる。**

### 段階 0: 配線とレベルの確認

3.2 節の 1〜3 を実施する。

- **成功条件**: XOUT のアイドルが 0V、`BSAVE` で 5V に振れる。
- ここで極性が想定と逆（アイドル 5V）だった場合、2.3 節の対応表を全面的に
  見直す。ファームウェアの `CFG invout` / `CFG invin` で吸収する。

### 段階 1: 実機の波形を測って時間軸を較正する

**この実験でいちばん重要な段階。** 以降のすべてがここで決まる値に乗る。

対象は**最小のプログラム**にする。`10 REM UUUU` の 1 行
（本体 22 バイト、`.bin` は 70 バイト）が既にエミュレータ側の基準として
使えるので、実機にも同じものを打ち込む。

```
python host/g850ctl.py -p COM5 cal --timeout 90 --save cal-real.json --apply
（表示が出たら実機で BSAVE を実行する）
```

`CAL` は**転送の全区間**（7 万本を超えるエッジ）を対象に、
パルス幅のヒストグラムを 1usec 刻みで積む。エッジを 1 本ずつ保存する
`RAW` は RAM に 3072 本しか入らず、ヘッダの 0 が 1 万個続く区間で
埋まってしまうので、較正には使えない。

- **測る値と期待値**

  | 測るもの | 期待（推定）| 意味 |
  |:--|--:|:--|
  | H の短いかたまりの最頻値 | 162 usec | ビット 0 |
  | H の長いかたまりの最頻値 | 406 usec | ビット 1 |
  | 1ms を超える H | 30 ms が **4 回** | ブロックの区切り |
  | 1ms を超える L | 8000 / 2000 / 24 / 6 / 4000 ms | PULSES |
  | 全体の所要時間 | 23〜26 秒 | |

- **成功条件**
  1. H のヒストグラムが**きれいに 2 つのかたまりに分かれる**
     （散らばっていたら取りこぼしを疑う。`ovf` の値を見る）
  2. 1ms 超の H がちょうど 4 回
  3. L の長いものが 5 本（8s / 2s / 24ms / 30ms を挟んで 6ms / 4s）
- **注意**: PULSES1 の L が 8 秒あるため、**最低 40 秒は観測窓を取る。**
  最初の数秒は「何も出ていない」ように見える。

得られた値はそのまま `CFG bit0` / `CFG bit1` / `CFG mark` / `CFG p1l` … へ
反映する（`--apply`）。**推定値ではなく実測値で送出するのが目的。**

この段階の副産物として **エミュレータの 9/8 換算が正しかったかが確定する。**
実測 ÷ エミュレータ実測（145 / 360 / 27000 usec）を計算して記録する。

- 比が 1.125 前後なら 9/8 換算は妥当だった
- 2.25 前後なら実機が 4MHz で動いていた（`67H` の設定）ことになる
- 3 つの比がばらばらなら、単一のクロック差では説明がつかない。
  ヘッダとデータで違うルーチンを通っている可能性を疑う

補助として `RAW` も併用する。こちらはエッジの並び順が分かるので、
**PULSES の順序**（H30ms → L8s → … ）が資料どおりかを目で確かめられる。
較正には `CAL`、構造の確認には `RAW`、と使い分ける。

### 段階 2: 取り込みと復号（実験 B）

`CAP` で PWM を復号し、`.bin` を復元する。

- **成功条件（BASIC）**
  1. 区切り 4 回で正常に終了する
  2. PWM1 が 48 バイト + パリティ 2 バイトで、パリティが一致する
  3. ヘッダの `0x00` が `0x02`（BASIC）、`0x12`-`0x13` の申告サイズと
     PWM2 の実バイト数が一致する
  4. PWM2 のパリティが一致する
  5. 復元した `.bin` が、**同じプログラムをエミュレータで `BSAVE` した
     `.bin` とバイト単位で一致する**
- **成功条件（バイナリ）**: 実機で `BSAVE M &H2400,&H2411` を実行し、
  ヘッダの `0x00` が `0x01`、`0x14`-`0x15` が `0x2400`、
  本体が実機のメモリ内容と一致する。
- 5. が通れば**実機とエミュレータのファイル互換が証明される。**

大きいデータでも試す。ROM 内蔵の BASE 変換プログラム（本体 2806 バイト）は
エミュレータ側で `.bin` の基準がすでに取れているので、比較対象として最適。

### 段階 3: 再生（実験 A）

**段階 1 で較正した値が入っていることを `CFG` で確認してから始める。**

送出の前に、実機なしで 2 つ潰しておく。

```
python host/g850ctl.py -p COM5 load out.bin
python host/g850ctl.py -p COM5 -v cfg          # 較正値が入っているか目視
（DECTEST を送る: ビット列の往復。実機も配線も要らない）
python host/g850ctl.py -p COM5 selftest        # D3→D2 のジャンパで幅を読み返す
```

`selftest` の H のヒストグラムが、段階 1 で実機から測った値と
**同じかたまりになっていること**を確かめる。ここが合っていないのに
実機へ流しても意味がない。

そのうえで段階 2 で得た `.bin`、およびエミュレータ由来の `.bin` を送出する。

手順:

1. `LOAD` で `.bin` を Arduino へ送る
2. 実機で `NEW`（BASIC の場合）を実行して中身を消す
3. 実機で `BLOAD` を実行する（待ち状態になる）
4. ホストで `PLAY` を実行する

`BLOAD` はポート `0x1F` をポーリングして待ち続けるので、**実機側を先に待たせて
から送出する**のが確実。`PLAY` に開始遅延を持たせて順序を緩める。

- **成功条件**
  1. エラーを出さずに完了する（`ERROR 80` = パリティ不一致が出ないこと）
  2. `LIST` で元のプログラムが戻っていること
  3. 戻したものを再度 `BSAVE` → `CAP` して、**送出した `.bin` と一致すること**
- **バイナリ**: `BLOAD M` / `BLOAD M &H2600` でアドレス指定の挙動も確かめる。
- **失敗したときの切り分け**

  | 症状 | 疑うところ | 確かめ方 |
  |:--|:--|:--|
  | 何も反応しない（`BLOAD` が待ち続ける）| XIN の極性、`0x15` の Xin 入力イネーブル、配線 | `CFG invout 1` で反転して再試行。段階 0 に戻って電圧を測る |
  | `ERROR 80`（パリティ不一致）| ビット幅が判定しきい値の境目にある | `CFG bit0` / `bit1` を段階 1 の実測値の ±10% で振る |
  | PWM1 だけ通って PWM2 で落ちる | ヘッダの長さが足りない | `PROFILE REAL` に戻す（短縮していたら） |
  | 途中で止まる | ホストの USB が詰まって送出がずれた | 進捗表示を減らす。`-v` を外す |

  **切り分けの起点は必ず `SELFTEST`。** 自分の出力が正しいと確認できていれば、
  残るのは実機側の判定条件だけになる。

### 段階 4: 短縮波形の下限を実機で測る

エミュレータでは PWM1 ヘッダ 1800〜2000 ビット、PWM2 ヘッダ 1000〜2000 ビットが
下限で、PULSES の長い L は 1/100 にしても通った。**同じことが実機でも
成り立つかを確かめる。**

- `CFG hdr1` / `CFG hdr2` / `CFG p1l` などを振りながら `PLAY` を繰り返す。
- **判定を確実にするため、試行ごとに `REM` の内容を変えて一意な目印にする。**
  同じ内容だと前回の残骸を拾って成功に見えることがある
  （エミュレータ側の実験で実際に踏んだ罠）。
- **成功条件**: 実機での下限を数値で確定させ、安全率 2 倍を取った
  推奨値（`PROFILE FAST`）を決める。
- 期待される効果: 22 バイトで 26 秒 → 3 秒程度。

### 段階 5（任意）: TEXT モードの SIO

余力があれば。`0x1F` bit1 が 11pin のどのピンなのか（pin-9 ACK = CTS と推定）を
実機で確定させる。

- `ACK` コマンドで pin-9 を H/L に振りながら実機で `TEXT` → `Sio` → `Save` を実行し、
  `--- SENDING ---` が動き出す条件を調べる。
- 動き出したら `RAW` で調歩同期のフレームを観測し、
  ボーレートが `Format` の設定どおりかを確かめる。

これは [text-sio.md](../../docs/analysis/text-sio.md) の「未確認事項」に
直接答えるものだが、**本実験の主目的ではないので段階 4 までを優先する。**

## 7. 想定されるリスク

| リスク | 対策 |
|:--|:--|
| 実機の 11pin が 5V でなく 3.3V 系だった | 段階 0 で通電前に実測する。3.3V なら Arduino 側を分圧するか、レベル変換を挟む |
| Arduino と実機が同時に同じ線を駆動する | XIN 側に 1kΩ 直列。Arduino の D3 は既定で入力にしておき、`PLAY` の間だけ出力にする |
| USB シリアルの送信が詰まってエッジを取りこぼす | キャプチャは割り込み + リングバッファ。ホストが読まないときは書き込みを捨てる（`availableForWrite` を見る）|
| 送出中のジッタでビットが誤判定される | 絶対時刻でスケジュールし、誤差を累積させない。162 usec と 406 usec の差は大きく、しきい値まで 80 usec 以上の余裕がある |
| 割り込み割り当てが D2 で効かない | `CFG capmode 1` でポーリング方式に切り替えられるようにしておく |
| `BLOAD` 中に BREAK 相当の入力が入って中断する | BREAK は `0x1F` bit7（キー側）。11pin とは別系統なので通常は影響しないが、中断したら再実行する |

## 8. この実験で答えを出したい未確認事項

既存ドキュメントに残っている項目のうち、実機があれば決着するもの。

- `0x1F` bit2（XIN）の**極性**（段階 0・3）
- エミュレータの 9/8 クロック換算の妥当性（段階 1）
- 実機での**短縮波形の下限**（段階 4）
- `BLOAD "名前"` が名前を照合するのか（段階 3 のついでに、
  ヘッダのファイル名を変えて試す）
- `0x1F` bit1 に対応する 11pin のピン（段階 5）
- `BSAVE` / `BLOAD` が `BUSY` (pin-4) / `ACK` (pin-9) を実際に使っているか（段階 1 で監視）
