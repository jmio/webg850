# 送出・復号する波形の定義

`BSAVE` / `BLOAD` が 11pin に出す PWM 信号の定義と、**実機で測った値**。

信号形式そのものの解析経緯は
[../../docs/analysis/bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md)、
`.bin` のファイル形式は
[../../docs/emulator/bsave-file-format.md](../../docs/emulator/bsave-file-format.md) にある。
本ドキュメントは**実機の値をここに集める**のが目的。

## 全体の構成

```
PULSES1 : H(mark) → L(p1l)
PWM1    : 0×hdr1 → 1×hdr1o → 0×hdr1z2 → START(1)
          → [1+8bit]×48 → [1+8bit]×2(パリティ) → STOP(1)
PULSES2 : L(p2l) → H(mark) → L(p2s1) → H(mark) → L(p2s2)
PWM2    : 0×hdr2 → 1×hdr2o → 0×hdr2z2 → START(1)
          → [1+8bit]×N → [1+8bit]×2(パリティ) → STOP(1)
PULSES3 : L(p3l) → H(mark)
```

- **区切りの長い H は 1 回の転送にちょうど 4 回**（PULSES1 に 1、
  PULSES2 に 2、PULSES3 に 1）。4 回目で転送終了と判断できる。
- PWM1 のデータ部が `.bin` の先頭 48 バイト、PWM2 のデータ部が
  49 バイト目以降。
- データは **MSB ファースト**。各バイトの前に必ず 1 のスタートビットが付く。
- パリティは**データ部の 8 ビット群に含まれる 1 の総数**を
  16 ビット・ビッグエンディアンにしたもの。パリティ自身は数に入れない。

## 極性（実機で確定・2026-08-30）

**11pin は出力と入力で極性が違う。** これは実機に信号を注入して初めて分かった。

| ポート | ビット | 11pin | 物理レベル | 向き |
|:--|:--|:--|:--|:--|
| `0x18` (out) | bit7 | pin-7 XOUT | **1 → 5V (H)** / 0 → 0V (L) | 非反転 |
| `0x1F` (in) | bit2 | pin-6 XIN | **1 ⟺ 0V (L)** / 0 ⟺ 5V (H) | **反転** |

**実機の XIN を駆動するときは反転させること。** ファームウェアの既定値は
`invout=1`（反転あり）、`invin=0`（反転なし）で、この実測に合わせてある。

XIN はカセットの再生側から来る信号をコンパレータで受ける入力なので、
その段で反転しているものと思われる。XOUT は録音側へ出す素の
デジタル出力なので反転しない。

### なぜ推定では埋まらなかったか

**PWM 波形が対称（各ビットが「H を t、L を t」）だから。**

極性が反転しても、受信側が測る H 期間は送信側の L 期間になるだけで
**長さは同じ**。つまり**ビットの値は正しく復号されてしまう**。
狂うのは PULSES と区切りパルスの解釈だけである。

そのため:

- **エミュレータの実装は証拠にならない。** 内部で閉じた往復なので
  `out18()` と `in1f()` の極性が揃ってさえいれば動く
- **実機同士の転送も証拠にならない。** 同じ対称性で成立してしまう
- **外部資料のレベル表は SIO モードの記述**で、入力バッファの反転までは書かれていない

### 反転したまま送ると何が起きるか（実測した症状）

| 送出 | 反転入力の実機が見るもの |
|:--|:--|
| アイドル L (0V) | **常に H** → 信号が来ていると誤認し続ける |
| 区切り H 30ms | L 30ms → **区切りとして認識されない** |
| ビット（H t / L t）| L t / H t → **幅は同じなので値は正しい** |

実機は `BLOAD` の待ち状態から抜けず、**データブロックの長さ（PWM1 の 3.4 秒、
PWM2 の 8.5 秒）に合わせてブザーが鳴った。** カセットインタフェースの
モニタ音と思われ、「データは届いているが枠が合っていない」ことの表れだった。
BREAK で抜けてもエラーは出ない。

### 未解決

**実機同士（`BSAVE M` → `BLOAD M`）はどう成立しているのか。**
A の XOUT（bit7=1 → 5V）を B の XIN が受けると bit2=0 になる計算で、
PULSES の解釈がずれるはずである。ビット値だけは対称性で正しく通るので、
区切りの検出だけ別の仕組みがあるのかもしれない。未確認。

## ビットの表し方

| ビット | 波形 |
|:--|:--|
| 0 | H を `bit0` usec → L を `bit0` usec |
| 1 | H を `bit1` usec → L を `bit1` usec |

**ビットの値は H の長さだけで決まる。L の長さは受信側が見ていない。**
（[bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md) の実測）

この性質は実装上とても効く。送出中に L の期間へ進捗表示などの処理を
挟んでも復号結果に影響しない。ファームウェアはこれを利用して、
区間ごとに `micros()` を取り直すやり方でジッタを L 側にだけ逃がしている。

受信側は立ち上がりを検出してから `bit0 × 1.5` 後の値を取り込めばよい、と
外部資料にある。しきい値の実体（ROM のカウント値）はまだ確かめていない。

## タイミングの値

### 推定値（実機で測る前）

エミュレータの実測値を 9/8 倍したもの。外部資料の実機実測とも一致する。
ファームウェアの `PROFILE REAL` の初期値。

| 定数 | 推定値 | 根拠 |
|:--|--:|:--|
| `bit0` | 162 usec | エミュレータ実測 145 × 9/8。外部資料の実機実測 162 |
| `bit1` | 406 usec | エミュレータ実測 360 × 9/8。外部資料の実機実測 406 |
| `mark` | 30 ms | エミュレータ実測 27ms × 9/8。外部資料 30ms |
| `p1l` | 8000 ms | 外部資料 |
| `p2l` | 2000 ms | 外部資料 |
| `p2s1` | 24 ms | 外部資料 |
| `p2s2` | 6 ms | 外部資料 |
| `p3l` | 4000 ms | 外部資料 |
| `hdr1` | 10000 / 40 / 40 | 外部資料。エミュレータの復号で完全一致を確認済み |
| `hdr2` | 25848 / 20 / 20 | 同上 |

**9/8 という比はエミュレータのクロック設定（9000 kHz）と実機の推定値
（8 MHz）から出しただけで、実機で測ったものではない。**
実機の CPU クロックはポート `67H` で 8MHz / 4MHz が切り替わるため、
`BSAVE` の実行中にどちらであるかによって倍半分ずれうる。

### 実測値（実機・2026-08-30 確定）

`CAL` で実機の `BSAVE`（`10 REM UUUU`、転送 26.16 秒、エッジ 73275 本）を測った。

| 定数 | **実測** | 推定値 | 差 |
|:--|--:|--:|--:|
| `bit0` | **162** µs（平均 161.8、36413 個）| 162 | **0%** |
| `bit1` | **406** µs（平均 406.0、214 個）| 406 | **0%** |
| `mark` | **30021** µs | 30000 | +0.07% |
| `p1l` | **7,965,382** µs | 8,000,000 | −0.43% |
| `p2l` | **2,008,226** µs | 2,000,000 | +0.41% |
| `p2s1` | **23,969** µs | 24,000 | −0.13% |
| `p2s2` | **6,013** µs | 6,000 | +0.22% |
| `p3l` | **3,998,066** µs | 4,000,000 | −0.05% |
| 転送全体 | **26.16** 秒 | 26.26 秒 | −0.4% |

**推定値（9/8 換算）はすべて 0.5% 以内で当たっていた。**

L 側は `bit0` が 164 µs、`bit1` が 404 µs。**H より L が約 2µs 長い。**
ROM のビットバンギングのループが左右非対称ということだが、
受信側は H の長さしか見ないので復号には影響しない。

### エミュレータとの比 — 実機は 8.00 MHz

| 定数 | 実機 | エミュレータ実測 | 比 |
|:--|--:|--:|--:|
| `bit0` | 162 µs | 145 µs | 1.117 |
| `bit1` | 406 µs | 360 µs | 1.128 |
| `mark` | 30021 µs | 27000 µs | 1.112 |
| 転送全体 | 26.16 秒 | 23.34 秒 | 1.121 |

**4 つの独立した量がすべて 1.11〜1.13 に収まった。** エミュレータの既定クロック
9000 kHz に対し、**実機の実効クロックは 8.00 MHz** で確定。
ポート `67H` の 4MHz 側（比が 2.25 になるはず）では動いていない。

これで [bsave-signal-format.md](../../docs/analysis/bsave-signal-format.md) の
「エミュレータのクロックは実機より約 11% 速い」という推定が実機で裏付けられた。

### PULSES の構成（実機・順序も資料どおり）

```
[0] H   30021 us   PULSES1 の区切り
[1] L 7965382 us   PULSES1 の L
[2] L 2008226 us   PULSES2 の L
[3] H   30018 us   PULSES2 の区切り
[4] L   23969 us   PULSES2 の中間 L
[5] H   30024 us   PULSES2 の区切り
[6] L    6013 us   PULSES2 の最後の L
[7] L 3998066 us   PULSES3 の L
[8] H   30021 us   PULSES3 の区切り
```

**区切りの H がちょうど 4 本、長い L が 5 本。**

## 短縮波形

実機の波形をそのまま流すと、22 バイトで 26 秒かかる。待ち時間の大半は
PULSES の長い L と、ヘッダの 0 の並びである。

エミュレータ上で下限を実測した結果（[bsave-bload.md](../../docs/emulator/bsave-bload.md)）:

| 変えたもの | 下限 |
|:--|:--|
| PWM1 のヘッダ | **1800〜2000 ビット** |
| PWM2 のヘッダ | **1000〜2000 ビット** |
| PULSES の長い L | 1/100 にしても影響なし |

これを踏まえた `PROFILE FAST` の値（下限の約 2 倍の余裕）:

| 定数 | FAST | REAL |
|:--|--:|--:|
| `p1l` | 80 ms | 8000 ms |
| `p2l` | 20 ms | 2000 ms |
| `p3l` | 40 ms | 4000 ms |
| `hdr1` | 4000 | 10000 |
| `hdr2` | 4000 | 25848 |

22 バイトで 26 秒 → 約 3.2 秒になる。

### 実機での下限（2026-08-30 実測）

`hdr1` = `hdr2` を振って `BLOAD` の成否を見た。PULSES の長い L は 1/100 に固定。

| `hdr1`/`hdr2` | 所要 | 結果 |
|--:|--:|:--|
| 4000 | 3.33 秒 | **成功** |
| 2000 | 1.99 秒 | **成功** |
| 1750 | 1.83 秒 | 失敗 |
| 1500 | 1.66 秒 | 失敗 |
| 1000 | 1.33 秒 | 失敗 |

**実機の下限は 1750〜2000 ビット。** エミュレータで測った PWM1 の下限
（1800〜2000）とほぼ完全に一致した。**エミュレータ上での短縮実験の結果は
実機にそのまま移せる。**

`PROFILE FAST` の 4000 は下限の 2 倍で、実機での動作も確認済み。
PULSES の長い L を 1/100 にしても影響が無いことも確認できた。

**ただし各設定は 1 回しか試していない。** 下限ぎりぎりの 2000 を常用せず、
4000 を使うこと。

## 取り込み時の判定

| 定数 | 既定 | 意味 |
|:--|--:|:--|
| `capgl` | 40 usec | これ以下の H はノイズとして捨てる |
| `capbit` | 280 usec | H がこれ未満ならビット 0、以上なら 1 |
| `capmark` | 1500 usec | H がこれ以上なら区切り |

`capbit` は `bit0` と `bit1` のほぼ中間。162 と 406 に対して
どちらからも 80 usec 以上の余裕がある。`capmark` は 406 と 30000 の
間ならどこでもよい。

較正 (`CAL`) を実行すると、実測したかたまりの中間値が `capbit` に入る。
実機で測った値は `capbit=284`、`capmark=7505`。ビット 0 の最頻 162 からは 122 µs、
ビット 1 の最小 392 からは 108 µs の余裕があり、2 群は完全に分離している。

### ノイズへの備え

実機から取り込むと、主要な 2 群のほかに幅 338 µs / 536 µs の外れパルスが
数本混じることがある（ブレッドボード配線での実測）。これは `capbit` を超えるので
「1」と判定され、**25848 個の 0 が並ぶ PWM2 のヘッダの途中に 1 が現れると
読み飛ばしが途中で終わり、9 ビットの枠が 1 ビットずれる。**

対策は 2 つ組み合わせる。どちらか一方では足りない。

| 対策 | 効く相手 |
|:--|:--|
| XOUT に 100Ω 直列 + 100nF を GND へ（時定数 10 µs の LPF）| 40 µs 未満の短いスパイク |
| `PWM_MIN_ONES = 5`（5 個未満の孤立した 1 はノイズとして 0 に戻す）| 338 / 536 µs の長い外れパルス |

実機のヘッダは 1 が 20 個（PWM2）ないし 40 個（PWM1）続くので、
しきい値 5 には 4 倍の余裕がある。

## 検算に使える既知の値

`10 REM UUUU` の 1 行だけのプログラム（`.bin` は 70 バイト）:

| | 値 |
|:--|:--|
| PWM1 のデータ | `02` + 空白 16 + `0d` + `16 00` + … （48 バイト）|
| PWM1 のパリティ | `0018` (= 24) |
| PWM2 のデータ | `ff 00 03 00…00 0a 07 fe 59 55 55 55 55 0d`（22 バイト）|
| PWM2 のパリティ | `002D` (= 45) |
| PWM1 の総ビット数 | 10532（ヘッダ 10080 + 1 + 9×50 + 1）|
| PWM2 の総ビット数 | 26106（ヘッダ 25888 + 1 + 9×24 + 1）|
| 合計ビット数 | **36638**（うち 1 が **213** 個、0 が **36425** 個）|

**ビット 0 / 1 の個数はエミュレータが実機の `BSAVE` を取り込んだときの実測
（36,425 / 213）と完全に一致する。** 同じ `.bin` から組み立てたビット列が
ROM の出力と同じ構成になることの裏付けになる。

ROM 内蔵の BASE 変換プログラム（`.bin` は 2854 バイト）:

| | 値 |
|:--|:--|
| PWM1 のパリティ | `001D` |
| PWM2 のパリティ | `2304` |

どちらも `host/pwmcodec.py selftest` で往復一致を確認済み。
実機から取り込んだ結果がこれと合えば、復号は正しい。
